Chapter 9 · Virtual Memory

How an OS runs programs bigger than RAM itself — a page at a time

Chapter 8 assumed a whole process had to sit in memory before it could run. Chapter 9 breaks that assumption: with virtual memory, only the pages actually being used are ever brought into RAM. This chapter covers demand paging, copy-on-write, page-replacement algorithms, frame allocation, thrashing, kernel memory allocation, and how Windows manages it all in practice.

Chương 8 giả định cả tiến trình phải nằm trọn trong bộ nhớ mới chạy được. Chương 9 phá vỡ giả định đó: với virtual memory, chỉ những trang thực sự đang dùng mới được nạp vào RAM. Chương này gồm demand paging, copy-on-write, các thuật toán page-replacement, cấp phát frame, thrashing, cấp phát kernel memory, và cách Windows quản lý tất cả trong thực tế.

Summary — Silberschatz Ch.9 (slide 86–89)
  • Virtual memory abstracts physical memory into an extremely large uniform array of storage.
  • Virtual memory trừu tượng hóa bộ nhớ vật lý thành 1 mảng lưu trữ đồng nhất cực lớn.
  • Benefits: (1) a program can be larger than physical memory, (2) a program does not need to be entirely in memory, (3) processes can share memory, and (4) processes can be created more efficiently.
  • Lợi ích: (1) chương trình có thể lớn hơn bộ nhớ vật lý, (2) không cần nạp trọn vẹn vào bộ nhớ, (3) tiến trình có thể dùng chung bộ nhớ, (4) tạo tiến trình hiệu quả hơn.
  • Demand paging is a technique whereby pages are loaded only when they are demanded during execution. A page fault occurs when a page not currently in memory is accessed.
  • Demand paging là kỹ thuật chỉ nạp trang khi nó thực sự được yêu cầu trong lúc chạy. Page fault xảy ra khi truy cập 1 trang hiện không có trong bộ nhớ.
  • Copy-on-write allows a child process to share the same address space as its parent; a copy is made only when either writes (modifies) a page.
  • Copy-on-write cho phép tiến trình con dùng chung không gian địa chỉ với cha; chỉ copy khi 1 trong 2 bên ghi (sửa) trang đó.
  • When memory runs low, a page-replacement algorithm selects an existing page to replace: FIFO, optimal, LRU — pure LRU is impractical, so most systems use LRU-approximation algorithms.
  • Khi bộ nhớ cạn, 1 thuật toán page-replacement chọn ra 1 trang hiện có để thay thế: FIFO, optimal, LRU — LRU thuần không khả thi, nên hầu hết hệ thống dùng thuật toán xấp xỉ LRU.
  • Global replacement selects from any process's frames; local replacement selects only from the faulting process's own frames.
  • Global replacement chọn frame từ bất kỳ tiến trình nào; local replacement chỉ chọn trong các frame của chính tiến trình bị fault.
  • Thrashing occurs when a system spends more time paging than executing. A locality is a set of pages actively used together; a working set is based on locality.
  • Thrashing xảy ra khi hệ thống tốn thời gian paging nhiều hơn thời gian chạy thật. 1 locality là tập trang đang dùng cùng nhau; working set dựa trên locality.
  • Kernel memory is allocated differently, in contiguous chunks of varying sizes, via the buddy system or slab allocation.
  • Kernel memory được cấp phát khác, theo khối liên tục kích thước thay đổi, qua buddy system hoặc slab allocation.
  • Linux, Windows, and Solaris manage virtual memory similarly, using demand paging and copy-on-write; each also uses a variation of LRU approximation known as the clock algorithm.
  • Linux, Windows, Solaris quản lý virtual memory tương tự nhau, dùng demand paging và copy-on-write; mỗi hệ đều dùng 1 biến thể xấp xỉ LRU gọi là clock algorithm.

Why bring in only part of the program, and what that buys you

Vì sao chỉ nạp 1 phần chương trình vào bộ nhớ, và điều đó mang lại lợi ích gì

Chapter 8 treated a process as an all-or-nothing block that had to sit fully in RAM. Virtual memory questions that assumption: most of a program's code is rarely touched, so why load it all?

Chương 8 coi 1 tiến trình như 1 khối tất-cả-hoặc-không-gì phải nằm trọn trong RAM. Virtual memory đặt lại câu hỏi đó: phần lớn mã của chương trình hiếm khi được dùng tới, vậy sao phải nạp hết?

1Quan sát: chương trình hiếm khi dùng hết chính nó

Code needs to be in memory to be executed, but the entire program is rarely used all at once — error-handling code, unusual routines, and large data structures that only apply in rare cases often sit untouched for an entire run.

Code cần nằm trong bộ nhớ mới thực thi được, nhưng toàn bộ chương trình hiếm khi được dùng hết cùng lúc — mã xử lý lỗi, các routine hiếm gặp, cấu trúc dữ liệu lớn chỉ áp dụng cho trường hợp hiếm thường nằm im suốt cả lần chạy.

Motivation: consider the ability to execute a partially-loaded program. The program is no longer constrained by the limits of physical memory — each program takes less memory while running, so more programs run at the same time.

Động lực: hãy xem xét khả năng chạy 1 chương trình chỉ được nạp 1 phần. Chương trình không còn bị giới hạn bởi dung lượng bộ nhớ vật lý — mỗi chương trình tốn ít bộ nhớ hơn khi chạy, nên nhiều chương trình chạy cùng lúc hơn.

2Virtual Address Space: khoảng trống chờ sẵn để lớn lên

The virtual address space is the logical (virtual) view of how a process is stored in memory — it usually starts at address 0 with contiguous addresses until the end of the space, while physical memory is organized in page frames.

Virtual address space là góc nhìn logic (ảo) của cách 1 tiến trình được lưu trong bộ nhớ — thường bắt đầu tại địa chỉ 0 với các địa chỉ liên tục tới hết không gian, trong khi bộ nhớ vật lý được tổ chức thành page frame.

The MMU must map logical to physical addresses — the same role it played in Chapter 8's paging hardware, now extended so a page can also point to disk instead of RAM.

Usually the logical address space is designed so the stack starts at the max logical address and grows "down", while the heap grows "up" — maximizing address-space use. The unused space between the two is a hole: no physical memory is needed until heap or stack actually grows into it.

3Shared Library dùng chung qua Virtual Memory

A shared library's pages are mapped into the virtual address space of several processes at once — the library's code exists as one physical copy in RAM, while each process's virtual address space simply points to it.

Shared library có các trang được ánh xạ vào virtual address space của nhiều tiến trình cùng lúc — mã của thư viện chỉ tồn tại dưới dạng 1 bản vật lý duy nhất trong RAM, trong khi virtual address space của mỗi tiến trình chỉ trỏ tới nó.

02 · Kỹ thuật chính

Bring a page into memory only the moment it's actually needed

Chỉ nạp 1 trang vào bộ nhớ đúng vào lúc nó thực sự cần tới

Instead of loading an entire process at launch, a lazy swapper brings in pages one at a time, on demand — this single idea is the engine behind virtual memory.

Thay vì nạp cả tiến trình lúc khởi động, 1 "lazy swapper" nạp từng trang một, theo yêu cầu — ý tưởng duy nhất này chính là động cơ của virtual memory.

1Lazy swapper và khái niệm cơ bản

Could bring the entire process into memory at load time — or bring a page into memory only when it is needed: less I/O, less memory, faster response, more users.

Có thể nạp cả tiến trình vào bộ nhớ ngay lúc load — hoặc chỉ nạp 1 trang đúng khi nó cần tới: ít I/O hơn, tốn ít bộ nhớ hơn, phản hồi nhanh hơn, phục vụ được nhiều người dùng hơn.
🎵
Ví dụ đời thườngGiống Spotify: thay vì tải cả album về máy trước khi nghe, app chỉ tải bài hát bạn đang bấm phát — bài khác trong album vẫn nằm trên server tới khi bạn thực sự chọn nghe.

A lazy swapper never swaps a page into memory unless that page will be needed — a swapper that deals with individual pages (instead of whole processes) is called a pager. With swapping, the pager guesses which pages will be used before swapping a process out again, and brings in only those pages.

Lazy swapper không bao giờ swap 1 trang vào bộ nhớ trừ khi trang đó sẽ được dùng tới — 1 swapper xử lý từng trang (thay vì cả tiến trình) được gọi là pager. Với swapping, pager đoán những trang nào sẽ được dùng trước khi swap tiến trình ra lần nữa, và chỉ nạp đúng những trang đó.

Demand paging is similar to a paging system with swapping — the difference is in granularity: swapping a whole process vs. swapping individual pages.

Demand paging giống hệ thống paging kèm swapping — khác biệt ở mức độ chi tiết: swap cả tiến trình so với swap từng trang riêng lẻ.

New hardware functionality is needed in the MMU to implement demand paging. If the pages needed are already memory resident, there's no difference from non-demand paging. If pages needed are not memory resident, the OS must detect and load the page from storage — all without changing program behavior or requiring the programmer to change code.

Cần chức năng phần cứng mới trong MMU để cài đặt demand paging. Nếu trang cần dùng đã nằm sẵn trong bộ nhớ (memory resident), không có gì khác với paging không-demand. Nếu trang cần dùng chưa nằm trong bộ nhớ, OS phải phát hiện và nạp trang đó từ bộ lưu trữ — tất cả mà không làm thay đổi hành vi chương trình hay buộc lập trình viên sửa code.

2Valid-Invalid Bit: cờ đánh dấu trang đã ở trong RAM hay chưa

With each page-table entry, a valid–invalid bit is associated: v ⇒ the page is in-memory (memory resident); i ⇒ the page is not-in-memory. Initially the valid-invalid bit is set to i on all entries.

Mỗi mục page table có kèm 1 bit valid–invalid: v ⇒ trang đang nằm trong bộ nhớ (memory resident); i ⇒ trang không nằm trong bộ nhớ. Ban đầu bit valid-invalid được đặt là i ở mọi mục.
🎟️
Ví dụ đời thườngGiống vé xem phim "còn hiệu lực" hay "đã hết hạn" — soát vé (MMU) chỉ cần nhìn tem vé (bit v/i) là biết ngay có cho qua hay phải xử lý thêm, không cần tra cứu thủ công.

During MMU address translation, if the valid-invalid bit in a page-table entry is i, the result is a page fault. If the page is needed and the reference turns out to be invalid, the process aborts; if valid but simply not-in-memory, the OS brings the page to memory.

Trong lúc MMU dịch địa chỉ, nếu bit valid-invalid của 1 mục page table là i, kết quả là 1 page fault. Nếu trang được cần và tham chiếu đó thực sự không hợp lệ, tiến trình bị abort; nếu hợp lệ nhưng chỉ đơn giản chưa nằm trong bộ nhớ, OS sẽ nạp trang đó vào.

36 bước xử lý Page Fault

If there is a reference to a missed page, the first reference traps to the OS — a page fault. The OS looks at another table to decide: invalid reference → abort; or just not-in-memory → continue the sequence below.

Nếu có 1 tham chiếu tới trang bị thiếu, lần tham chiếu đầu tiên sẽ trap về OS — gọi là page fault. OS nhìn vào 1 bảng khác để quyết định: tham chiếu không hợp lệ → abort; hoặc chỉ là chưa-nằm-trong-bộ-nhớ → tiếp tục chuỗi bước dưới đây.
1 · Trap

Tham chiếu tới trang bị thiếu → trap về OS, báo page fault.

2 · Kiểm tra

OS tra bảng khác: invalid reference → abort; not-in-memory → tiếp tục.

3 · Tìm frame trống

Tìm 1 free frame trong bộ nhớ vật lý.

4 · Đọc đĩa

Swap trang cần vào frame đó qua 1 thao tác đĩa đã lên lịch (scheduled disk operation).

5 · Cập nhật bảng

Reset page table để đánh dấu trang đó nay đã nằm trong bộ nhớ: đặt bit valid-invalid = v.

6 · Restart

Khởi động lại đúng chỉ lệnh đã gây ra page fault.

412 bước Stages in Demand Paging — trường hợp xấu nhất

The "6 steps" above is a simplified view. In the worst case (no shortcuts, full disk wait), handling one page fault actually takes 12 fine-grained stages, which can be grouped into 4 phases: trap & detect, read from disk, I/O interrupt, resume process.

"6 bước" ở trên là bản đơn giản hóa. Trong trường hợp xấu nhất (không có đường tắt, phải đợi đĩa đầy đủ), xử lý 1 page fault thực ra gồm 12 giai đoạn chi tiết, có thể gom thành 4 nhóm: trap & phát hiện, đọc từ đĩa, ngắt I/O, tiếp tục tiến trình.
A · Trap & phát hiện (1–4)

1) Trap về OS. 2) Lưu lại thanh ghi & trạng thái tiến trình. 3) Xác định ngắt này là page fault. 4) Kiểm tra tham chiếu hợp lệ & xác định vị trí trang đó trên đĩa.

B · Đọc từ đĩa (5)

5Aspects, Instruction Restart & Free-Frame List

In the extreme case, a process can start with no pages in memory at all — the OS sets the instruction pointer to the first instruction, which is non-memory-resident, causing a page fault. If every process starts this way, it's called pure demand paging.

Trong trường hợp cực đoan, 1 tiến trình có thể khởi động mà không có trang nào trong bộ nhớ — OS đặt instruction pointer vào chỉ lệnh đầu tiên, vốn không nằm trong bộ nhớ, gây ra page fault. Nếu mọi tiến trình đều khởi động kiểu này, gọi là pure demand paging.

Actually, a given instruction could access multiple pages → multiple page faults — e.g., the fetch and decode of an instruction that adds 2 numbers from memory and stores the result back. The pain is decreased because of locality of reference (covered again in the Allocation & Thrashing tab).

Thực tế, 1 chỉ lệnh có thể truy cập nhiều trang cùng lúc → nhiều page fault — vd: fetch và decode của 1 chỉ lệnh cộng 2 số từ bộ nhớ và lưu kết quả lại. Mức độ "đau" này giảm bớt nhờ locality of reference (sẽ nói lại ở tab Allocation & Thrashing).

Instruction restart: consider an instruction that could access several different locations — e.g., a block move or auto increment/decrement location. Restarting the whole operation is tricky when source and destination overlap.

Instruction restart: xét 1 chỉ lệnh có thể truy cập nhiều vị trí khác nhau — vd block move hoặc vị trí auto increment/decrement. Khởi động lại toàn bộ phép toán khá rắc rối khi vùng nguồn và vùng đích chồng lấn lên nhau.

Most operating systems maintain a free-frame list — a pool of free frames for satisfying page-fault requests. The content of frames is typically zeroed-out before allocation, a technique called zero-fill-on-demand. When a system starts up, all available memory is placed on the free-frame list.

Hầu hết hệ điều hành duy trì 1 free-frame list — 1 nhóm frame trống để phục vụ các yêu cầu page fault. Nội dung của frame thường được xóa về 0 trước khi cấp phát, kỹ thuật này gọi là zero-fill-on-demand. Khi hệ thống khởi động, toàn bộ bộ nhớ khả dụng được đưa vào free-frame list.
Vì sao phải zero-out 1 frame trước khi cấp? — Lý do bảo mật: frame đó trước đây có thể từng chứa dữ liệu của 1 tiến trình khác (đã kết thúc). Nếu không xóa về 0, tiến trình mới được cấp frame này có thể "đọc trộm" được dữ liệu cũ còn sót lại — 1 lỗ hổng rò rỉ thông tin giữa các tiến trình.

6Performance of Demand Paging: Effective Access Time

Three major activities in a page-fault service: (1) service the interrupt — careful coding means just a few hundred instructions; (2) read the page — lots of time; (3) restart the process — again just a small amount of time.

3 hoạt động chính khi phục vụ 1 page fault: (1) xử lý interrupt — code cẩn thận thì chỉ tốn vài trăm chỉ lệnh; (2) đọc trang — tốn nhiều thời gian nhất; (3) khởi động lại tiến trình — lại chỉ tốn 1 lượng thời gian nhỏ.

Let the page-fault rate be p, 0 ≤ p ≤ 1: if p = 0, no page faults; if p = 1, every reference is a fault. Effective Access Time (EAT) = (1 − p) × memory access + p × (page fault overhead + swap page out + swap page in).

Gọi tỉ lệ page fault là p, 0 ≤ p ≤ 1: nếu p = 0, không có page fault nào; nếu p = 1, mọi tham chiếu đều fault. Effective Access Time (EAT) = (1 − p) × thời gian truy cập bộ nhớ + p × (chi phí page fault + swap ra + swap vào).

Memory access = 200ns, average page-fault service time = 8ms. EAT = (1−p)×200 + p×8,000,000 = 200 + p×7,999,800.

Nếu 1 trong 1.000 lần truy cập gây page fault (p = 0.001): EAT = 8.2μs — chậm hơn 40 lần so với bình thường!

Muốn giảm hiệu năng không quá 10%: cần p < 0.0000025, tức < 1 page fault trong mỗi 400.000 lần truy cập bộ nhớ.

Page fault cực kỳ đắt vì phải đợi đĩa (tính bằng ms) trong khi truy cập RAM chỉ tính bằng ns — chênh lệch hàng triệu lần khiến dù p rất nhỏ, EAT vẫn bị kéo lên đáng kể.

03 · Tối ưu fork()

Share first, copy only when someone actually writes

Dùng chung trước, chỉ copy khi có ai đó thực sự ghi

fork() traditionally meant duplicating the entire parent's address space for the child — demand paging makes a much cheaper trick possible: share everything, and copy lazily.

fork() theo kiểu truyền thống nghĩa là sao chép toàn bộ address space của cha cho con — demand paging giúp 1 mẹo rẻ hơn nhiều trở nên khả thi: dùng chung mọi thứ, và chỉ copy khi cần.

1Copy-on-Write (COW) hoạt động ra sao

Copy-on-Write (COW) allows both parent and child processes to initially share the same pages in memory. If either process modifies a shared page, only then is the page copied.

Copy-on-Write (COW) cho phép cả tiến trình cha và con ban đầu dùng chung các trang trong bộ nhớ. Nếu 1 trong 2 bên sửa đổi 1 trang dùng chung, lúc đó trang mới được copy.

Ví dụ đời thườngGiống Google Docs "Make a copy": file vẫn trỏ chung 1 bản gốc cho tới khi bạn thực sự gõ phím sửa đổi — lúc đó hệ thống mới tách ra 1 bản độc lập riêng cho bạn.

COW allows more efficient process creation, as only modified pages are copied — unmodified pages (which are often the majority: shared code, read-only data) never need duplicating at all.

COW giúp tạo tiến trình hiệu quả hơn nhiều, vì chỉ những trang bị sửa mới được copy — các trang không sửa (thường chiếm đa số: code dùng chung, dữ liệu chỉ-đọc) không bao giờ cần nhân bản.

2Pool zero-fill-on-demand và vfork()

In general, free pages are allocated from a pool of zero-fill-on-demand pages. This pool should always have free frames ready for fast demand-page execution — you don't want to have to free a frame as well as do other processing on a page fault.

Nói chung, các trang trống được cấp từ 1 pool trang zero-fill-on-demand. Pool này nên luôn có sẵn frame trống để demand-page nhanh — bạn không muốn vừa phải giải phóng 1 frame vừa phải xử lý thêm việc khác ngay lúc page fault.

vfork() is a variation on fork() where the parent is suspended, and the child uses the copy-on-write address space of the parent directly — no copying at all. vfork() is designed to have the child call exec() right away, and is very efficient.

vfork() là 1 biến thể của fork(): tiến trình cha bị tạm dừng, còn con dùng thẳng copy-on-write address space của cha — không copy gì cả. vfork() được thiết kế để con gọi exec() ngay sau đó, nên rất hiệu quả.
vfork() hiệu quả nhất khi con chỉ "mượn tạm" address space của cha trong tích tắc để gọi exec() nạp 1 chương trình hoàn toàn khác — lúc đó address space cũ của cha không còn ý nghĩa gì với con nữa.

04 · Khi hết frame

No free frame left — who gets evicted, and how do we decide?

Hết frame trống — ai bị đuổi ra, và quyết định dựa trên điều gì?

Memory is also in demand from the kernel, I/O buffers, and other processes — so page-replacement algorithms exist to pick a victim page wisely, minimizing future page faults.

Bộ nhớ cũng đang được kernel, I/O buffer, và các tiến trình khác tranh nhau dùng — nên các thuật toán page-replacement tồn tại để chọn 1 trang nạn nhân 1 cách khôn ngoan, giảm thiểu page fault trong tương lai.

1Vì sao cần Page Replacement

If there is no free frame — used up by process pages, also in demand from the kernel and I/O buffers — page replacement finds some page in memory that's not really in use, and pages it out. The algorithm matters: performance wants an algorithm resulting in the minimum number of page faults, and the same page may be brought into memory several times.

Nếu không còn frame trống — đã bị dùng hết bởi các trang tiến trình, cũng đang được kernel và I/O buffer tranh dùng — page replacement tìm 1 trang trong bộ nhớ hiện không thực sự đang dùng, rồi đẩy nó ra. Thuật toán quan trọng: hiệu năng cần 1 thuật toán cho số page fault ít nhất, và cùng 1 trang có thể bị nạp vào bộ nhớ nhiều lần.

Use a modify (dirty) bit to reduce overhead of page transfers — only modified pages are written to disk; clean (unmodified) victim pages can simply be discarded. Page replacement completes the separation between logical and physical memory: a large virtual memory can be provided on a smaller physical memory.

Dùng modify (dirty) bit để giảm chi phí chuyển trang — chỉ những trang đã sửa mới cần ghi ra đĩa; trang nạn nhân sạch (chưa sửa) có thể đơn giản bỏ đi luôn. Page replacement hoàn thiện sự tách rời giữa bộ nhớ logic và vật lý: 1 virtual memory lớn có thể được cung cấp trên 1 bộ nhớ vật lý nhỏ hơn.

5Optimal (OPT) Algorithm: chuẩn vàng không khả thi

The Optimal (OPT) algorithm replaces the page that will not be used for the longest period of time. On the reference string example, OPT gives 9 page faults — the fewest possible.

Vậy làm sao biết trước điều này? Bạn không thể đọc được tương lai — OPT chủ yếu được dùng để đo xem 1 thuật toán khác, khả thi thực tế, chạy tốt tới đâu, như 1 cận trên lý thuyết.

6Least Recently Used (LRU): dùng quá khứ thay vì tương lai

LRU uses past knowledge rather than future: replace the page that has not been used in the most amount of time, associating a time of last use with each page. On the example string, LRU gives 12 faults — better than FIFO but worse than OPT, and it's generally a good algorithm, frequently used in practice.

LRU dùng tri thức quá khứ thay vì tương lai: thay thế trang chưa được dùng trong khoảng thời gian dài nhất tính tới hiện tại, gắn thời gian dùng lần cuối cho mỗi trang. Trên ví dụ, LRU cho 12 fault — tốt hơn FIFO nhưng kém hơn OPT, và nó thường là 1 thuật toán tốt, được dùng rộng rãi trong thực tế.

Ví dụ đời thườngGiống dọn tủ quần áo chật: bạn bỏ đi cái áo mà lâu nhất chưa mặc tới (LRU), chứ không phải cái mua sớm nhất (FIFO) — vì áo mua sớm nhưng vẫn mặc thường xuyên thì không nên bỏ.

But how to implement LRU? Counter implementation: every page entry has a counter, every time a page is referenced copy the clock into the counter — replacing requires searching the whole table for the smallest value. Stack implementation: keep a stack of page numbers in a doubly-linked form; on each reference, move the page to the top — no search needed for replacement (it's the bottom of the stack), but each update is more expensive.

Nhưng cài đặt LRU ra sao? Cài đặt bằng counter: mỗi mục trang có 1 counter, mỗi lần trang được tham chiếu thì copy đồng hồ hệ thống vào counter đó — khi thay thế phải quét cả bảng tìm giá trị nhỏ nhất. Cài đặt bằng stack: giữ 1 stack các số trang dạng danh sách liên kết đôi; mỗi lần tham chiếu, đưa trang đó lên đỉnh — không cần tìm kiếm khi thay thế (luôn là đáy stack), nhưng mỗi lần cập nhật tốn kém hơn.
Ví dụ số (slide 38) trên reference string 4,7,0,7,1,0,1,2,1,2,7,1,2: để "nhấc" 1 trang đang nằm giữa stack lên đỉnh (dùng danh sách liên kết đôi), ta phải nối lại các con trỏ xung quanh nó rồi gắn nó lên đỉnh — với chuỗi ví dụ này, tổng cộng cần đổi tới 6 con trỏ. Đây chính là cái giá "mỗi lần cập nhật tốn kém hơn" của stack implementation.
LRU và OPT đều là stack algorithms — loại thuật toán không bị dính Belady's Anomaly, khác với FIFO.

7LRU Approximation: Reference Bit & Second-Chance (Clock)

LRU needs special hardware and is still slow in practice. A reference bit approximates it cheaply: with each page associate a bit, initially 0; when the page is referenced, the bit is set to 1. Replace any page with reference bit = 0, if one exists — but we don't know the order among them.

LRU thực sự cần phần cứng đặc biệt và vẫn chậm trong thực tế. Reference bit xấp xỉ nó với chi phí rẻ hơn: mỗi trang gắn 1 bit, ban đầu = 0; khi trang được tham chiếu, bit được đặt thành 1. Thay thế bất kỳ trang nào có reference bit = 0, nếu tồn tại — nhưng ta không biết được thứ tự giữa các trang đó.

The Second-chance (clock) algorithm is generally FIFO, plus a hardware-provided reference bit. If the page to be replaced has reference bit = 0 → replace it. If reference bit = 1: set the bit to 0, leave the page in memory, then move on and replace the next page, subject to the same rules.

Thuật toán Second-chance (clock) về cơ bản là FIFO, cộng thêm 1 reference bit do phần cứng cung cấp. Nếu trang định thay thế có reference bit = 0 → thay nó. Nếu reference bit = 1: đặt bit về 0, giữ trang lại trong bộ nhớ, rồi chuyển qua xét trang tiếp theo, theo đúng quy tắc tương tự.
🕐
Ví dụ đời thườngGiống kim đồng hồ quét quanh 1 vòng tròn các trang xếp theo vòng — trang nào vừa được "gãi ngứa" (dùng gần đây, bit=1) thì được tha 1 lần nữa (hạ bit về 0) và kim đi tiếp, trang nào "nguội" (bit=0) thì bị thay ngay.

Improve the algorithm by using reference bit and modify bit (if available) together: take the ordered pair (reference, modify).

(0,0)

9Counting, Page-Buffering, và ứng dụng

Counting algorithms keep a counter of the number of references made to each page — not common in practice. Least Frequently Used (LFU) replaces the page with the smallest count; Most Frequently Used (MFU) is based on the argument that the page with the smallest count was probably just brought in and has yet to be used.

Counting algorithms giữ 1 bộ đếm số lần tham chiếu tới mỗi trang — không phổ biến trong thực tế. Least Frequently Used (LFU) thay trang có count nhỏ nhất; Most Frequently Used (MFU) dựa trên lập luận rằng trang có count nhỏ nhất có lẽ vừa mới được đưa vào và chưa kịp dùng tới.

Page-buffering algorithms keep a pool of free frames, always — so a frame is available when needed, not searched for at fault time: read the page into a free frame and select a victim to evict and add to the free pool later, when convenient. Possibly keep a list of modified pages, and write them out when the backing store is otherwise idle.

Page-buffering algorithms luôn giữ sẵn 1 pool frame trống — để frame có sẵn khi cần, không phải tìm ngay lúc fault: đọc trang vào 1 frame trống rồi chọn nạn nhân để đuổi và thêm vào pool trống sau, khi thuận tiện. Có thể giữ 1 danh sách trang đã sửa, và ghi chúng ra khi backing store đang rảnh.

A third option: possibly keep the contents of a freed frame intact, and note what was in it — if that same page is referenced again before the frame gets reused for something else, there's no need to load its contents again from disk. This is generally useful to reduce the penalty if the "wrong" victim frame was selected.

1 lựa chọn thứ 3: có thể giữ nguyên nội dung của frame vừa giải phóng, và ghi chú lại trước đó nó chứa trang nào — nếu đúng trang đó bị tham chiếu lại trước khi frame bị tái sử dụng cho việc khác, không cần đọc lại nội dung từ đĩa nữa. Cách này nhìn chung giúp giảm thiệt hại nếu lỡ chọn nhầm victim frame.

05 · Cấp phát & sự cố

How many frames per process — and what happens if you get it wrong

Cấp bao nhiêu frame cho mỗi tiến trình — và điều gì xảy ra nếu cấp sai

Too few frames per process causes constant page faults; this section covers how the OS decides frame counts, and the nasty spiral — thrashing — that happens when it gets this wrong.

Quá ít frame cho mỗi tiến trình gây page fault liên tục; phần này nói về cách OS quyết định số frame, và vòng xoáy tệ hại — thrashing — xảy ra khi quyết định đó sai.

1Allocation of Frames: tối thiểu và tối đa

Each process needs a minimum number of frames. Example: IBM 370 needs 6 pages to handle an SS MOVE instruction — the instruction itself is 6 bytes and might span 2 pages (2 pages to handle "from", 2 pages to handle "to"). The maximum, of course, is the total frames in the system.

Mỗi tiến trình cần 1 số frame tối thiểu. Ví dụ: IBM 370 cần 6 trang để xử lý 1 chỉ lệnh SS MOVE — bản thân chỉ lệnh dài 6 byte và có thể trải trên 2 trang (2 trang cho "from", 2 trang cho "to"). Tối đa, dĩ nhiên, là tổng số frame của cả hệ thống.
🧰
Ví dụ đời thườngGiống thợ sửa xe cần tối thiểu 1 bộ dụng cụ cơ bản mới sửa được xe — thiếu dưới mức đó thì không thể làm việc, dù muốn cấp thêm bao nhiêu dụng cụ cũng được, miễn còn trong kho.

Two major allocation schemes: fixed allocation and priority allocation — plus any variations.

Priority allocation áp dụng kiểu tỉ lệ nhưng dựa trên priority thay vì kích thước: nếu tiến trình Pi gây page fault, chọn thay thế 1 frame của chính nó, hoặc 1 frame từ 1 tiến trình có priority number thấp hơn.

2Global vs. Local Replacement

Global replacement — a process selects a replacement frame from the set of all frames; one process can take a frame from another. Execution time can vary greatly, but throughput is generally higher, so it's more common.

Global replacement — 1 tiến trình chọn frame thay thế từ tập tất cả frame; 1 tiến trình có thể "cướp" frame của tiến trình khác. Thời gian chạy có thể thay đổi rất nhiều, nhưng throughput tổng thể thường cao hơn, nên phổ biến hơn.

Local replacement — each process selects from only its own set of allocated frames: more consistent per-process performance, but possibly underutilized memory overall.

Local replacement — mỗi tiến trình chỉ chọn trong tập frame đã cấp cho riêng nó: hiệu năng mỗi tiến trình ổn định hơn, nhưng có thể khiến bộ nhớ tổng thể bị dùng không hiệu quả.
🏙️
Ví dụ đời thườngGlobal giống bãi đỗ xe chung của cả tòa nhà — ai tới trước đỗ trước, có thể lấn chỗ của căn hộ khác. Local giống mỗi căn hộ có đúng 1 chỗ đỗ riêng — công bằng hơn nhưng nếu căn hộ đó đi vắng thì chỗ đỗ vẫn bỏ trống.

3Reclaiming Pages & NUMA

Reclaiming pages is a strategy to implement global page-replacement policy: rather than waiting for the free-frame list to drop to zero before selecting pages for replacement, page replacement is triggered when the list falls below a certain (minimum) threshold, and suspended once it rises back above a maximum threshold — ensuring there's always sufficient free memory for new requests.

Reclaiming pages là 1 chiến lược cài đặt chính sách global page-replacement: thay vì đợi free-frame list tụt về 0 mới bắt đầu chọn trang để thay, việc page-replacement được kích hoạt khi danh sách tụt xuống dưới 1 ngưỡng (tối thiểu) nhất định, và tạm dừng khi nó lên lại trên ngưỡng tối đa — đảm bảo luôn đủ bộ nhớ trống cho các yêu cầu mới.

Many systems are NUMA (Non-Uniform Memory Access) — speed of access to memory varies, e.g., CPU boards with their own local memory interconnected over a system bus. Optimal performance comes from allocating memory "close to" the CPU on which the thread is scheduled — Solaris solves this with lgroups, structures tracking CPU/memory low-latency groups.

Nhiều hệ thống là NUMA (Non-Uniform Memory Access) — tốc độ truy cập bộ nhớ thay đổi tùy vị trí, vd các board CPU với bộ nhớ cục bộ riêng, nối với nhau qua system bus. Hiệu năng tối ưu đạt được khi cấp bộ nhớ "gần" CPU mà thread đang chạy — Solaris giải quyết bằng lgroups, cấu trúc theo dõi các nhóm CPU/bộ nhớ có độ trễ thấp.
🏢

4Thrashing: khi hệ thống "chạy mà không chạy"

If a process does not have "enough" frames, the page-fault rate is very high: page fault → get frame → replace existing frame → but quickly need the replaced frame back → more processes get page faults → this leads to low CPU utilization, and the OS mistakenly thinking it needs to increase the degree of multiprogramming, adding yet another process to the already-struggling system.

Nếu 1 tiến trình không có "đủ" frame, tỉ lệ page fault rất cao: page fault → lấy frame → thay thế frame hiện có → nhưng rồi nhanh chóng lại cần đúng frame vừa thay → nhiều tiến trình khác cũng page fault theo → dẫn tới CPU utilization thấp, và OS lại tưởng nhầm rằng cần tăng mức đa chương, thêm 1 tiến trình nữa vào hệ thống vốn đã quá tải.

Thrashing: a process is busy swapping pages in and out — as the degree of multiprogramming increases, CPU utilization rises at first, then suddenly collapses once thrashing begins.

Thrashing: 1 tiến trình bận rộn swap trang vào ra liên tục — khi mức đa chương tăng lên, CPU utilization lúc đầu tăng theo, rồi bất ngờ sụp đổ khi thrashing bắt đầu.
🚦
Ví dụ đời thườngGiống kẹt xe giờ cao điểm: thêm 1 làn xe (thêm tiến trình) tưởng sẽ giúp thông thoáng hơn, nhưng quá đông xe cùng lúc khiến cả tuyến đường đứng hình — không ai di chuyển được, dù mọi xe đều đang "cố gắng chạy".

5Vì sao Demand Paging hoạt động — Locality Model

Why does demand paging work? The locality model: as a process executes, it moves from one locality to another, and localities may overlap. Why does thrashing occur? Σ size of locality > total memory size. Limit the effects by using local or priority page replacement.

Vì sao demand paging hoạt động được? Locality model: khi 1 tiến trình chạy, nó di chuyển từ locality này sang locality khác, và các locality có thể chồng lấn nhau. Vì sao thrashing xảy ra? Σ kích thước locality > tổng dung lượng bộ nhớ. Giới hạn ảnh hưởng bằng cách dùng page replacement kiểu local hoặc theo priority.

6Working-Set Model

Let Δ ≡ working-set window ≡ a fixed number of page references, e.g., 10,000 instructions. WSSi (working set of process Pi) = total number of pages referenced in the most recent Δ (varies over time).

06 · Bộ nhớ kernel

The kernel doesn't play by the same memory rules as user processes

Kernel không tuân theo luật cấp phát bộ nhớ giống như tiến trình user

Kernel data structures come in many odd sizes and sometimes need physically contiguous memory for device I/O — two dedicated allocators exist to serve exactly this need.

Các cấu trúc dữ liệu của kernel có nhiều kích thước lẻ khác nhau và đôi khi cần bộ nhớ liên tục vật lý cho device I/O — 2 bộ cấp phát chuyên dụng tồn tại chính để phục vụ nhu cầu này.

1Allocating Kernel Memory: khác user memory ở điểm nào

Kernel memory is treated differently from user memory. It's often allocated from a free-memory pool, since the kernel requests memory for structures of varying sizes — and some kernel memory needs to be contiguous, e.g., for device I/O.

Bộ nhớ kernel được xử lý khác với bộ nhớ user. Nó thường được cấp từ 1 pool bộ nhớ trống, vì kernel yêu cầu bộ nhớ cho các cấu trúc kích thước khác nhau — và 1 số bộ nhớ kernel cần liên tục (contiguous), vd cho device I/O.

2Buddy System (power-of-2 allocator)

Allocates memory from a fixed-size segment consisting of physically-contiguous pages, using a power-of-2 allocator: satisfies requests in units sized as a power of 2, rounding each request up to the next highest power of 2. When a smaller allocation is needed than is available, the current chunk splits into two buddies of the next-lower power of 2, continuing until an appropriately sized chunk is available.

Cấp bộ nhớ từ 1 đoạn kích thước cố định gồm các trang liên tục vật lý, dùng power-of-2 allocator: thỏa mãn yêu cầu theo đơn vị là lũy thừa của 2, làm tròn mỗi yêu cầu lên lũy thừa 2 gần nhất lớn hơn. 3Slab Allocator

An alternate strategy: a slab is one or more physically contiguous pages; a cache consists of one or more slabs. There is a single cache for each unique kernel data structure — e.g., for process descriptors, file objects, semaphores — each cache filled with objects, instantiations of that data structure.

1 chiến lược thay thế: 1 slab là 1 hoặc nhiều trang liên tục vật lý; 1 cache gồm 1 hoặc nhiều slab. Có 1 cache riêng cho mỗi cấu trúc dữ liệu kernel duy nhất — vd cho process descriptor, file object, semaphore — mỗi cache được lấp đầy bằng object, các bản thể hóa của cấu trúc dữ liệu đó.

When the cache is created, it's filled with objects marked as free; when structures are stored, objects are marked used. If a slab is full of used objects, the next object is allocated from an empty slab — if no empty slabs, a new slab is allocated.

Khi cache được tạo, nó được lấp đầy bằng các object đánh dấu free; khi cấu trúc được lưu, object được đánh dấu used. Nếu 1 slab đã đầy toàn object used, object tiếp theo được cấp từ 1 slab rỗng khác — nếu không còn slab rỗng, 1 slab mới được cấp phát thêm.
🧊
Ví dụ đời thườngGiống khay đá viên trong tủ lạnh: mỗi khay (slab) chỉ đựng đúng 1 loại kích thước viên đá (1 loại object), đã có sẵn các "ô khuôn" đúng hình dạng — không cần cắt gọt lại mỗi lần lấy ra dùng.

Benefits include no fragmentation and fast memory request satisfaction. Example in Linux: the process descriptor is of type struct task_struct, approx. 1.7KB — a new task allocates a new struct from cache, reusing an existing free struct if available.

Lợi ích gồm không fragmentation và đáp ứng yêu cầu bộ nhớ nhanh. Ví dụ trong Linux: process descriptor có kiểu struct task_struct, khoảng 1.7KB — 1 task mới cấp 1 struct mới từ cache, tái dùng struct trống sẵn có nếu còn.
Full

Slab toàn bộ object đã dùng (used).

Empty

Slab toàn bộ object còn trống (free).

Partial

Slab có cả object free lẫn used trộn lẫn.

Upon request, the slab allocator uses a free struct in a partial slab first; if none, takes one from an empty slab; if no empty slab, creates a new one. Slab started in Solaris, now wide-spread for both kernel and user memory in various OSes. Linux 2.2 had SLAB, now has both SLOB (Simple List of Blocks, for limited-memory systems) and SLUB (performance-optimized SLAB).

Khi có yêu cầu, slab allocator ưu tiên dùng struct trống trong 1 slab partial trước; nếu không có, lấy từ 1 slab empty; nếu không còn slab empty, tạo mới 1 slab. Slab khởi nguồn từ Solaris, nay phổ biến rộng rãi cho cả bộ nhớ kernel lẫn user trên nhiều OS. Linux 2.2 có SLAB, nay có cả SLOB (Simple List of Blocks, cho hệ thống ít bộ nhớ) và SLUB (SLAB tối ưu hiệu năng).

4Other Considerations: Pre-paging, Page Size, TLB Reach

Pre-paging reduces the large number of page faults that occur at process startup, by pre-paging some or all pages a process will need before they're referenced. But if pre-paged pages go unused, I/O and memory are wasted — if α near zero, pre-paging loses.

Pre-paging giảm số lượng page fault lớn xảy ra lúc khởi động tiến trình, bằng cách nạp trước 1 phần hoặc toàn bộ trang mà tiến trình sẽ cần, trước khi chúng thực sự được tham chiếu. Nhưng nếu trang nạp trước không được dùng tới, I/O và bộ nhớ bị lãng phí — nếu α gần 0, pre-paging phản tác dụng.
Phép so sánh chi phí (slide 74): giả sử s trang được pre-page, và α là tỉ lệ trong số đó thực sự được dùng tới. So sánh: chi phí của s·α page fault tiết kiệm được (nhờ pre-page đúng) so với chi phí của s·(1−α) trang nạp thừa (pre-page sai, lãng phí I/O + bộ nhớ). Nếu α gần 1 → pre-paging đáng giá; nếu α gần 0 → gần như toàn bộ công sức pre-page bị phí phạm, nên tránh dùng.

Page size selection must consider: fragmentation, page table size, resolution, I/O overhead, number of page faults, locality, TLB size and effectiveness — always a power of 2, usually in the range 2¹² (4,096 bytes) to 2²² (4,194,304 bytes), and growing on average over time.

Chọn page size phải cân nhắc: fragmentation, kích thước page table, độ phân giải, chi phí I/O, số page fault, locality, kích thước & hiệu quả TLB — luôn là lũy thừa 2, thường trong khoảng 2¹² (4.096 byte) tới 2²² (4.194.304 byte), và trung bình tăng dần theo thời gian.

TLB Reach — the amount of memory accessible from the TLB — equals TLB size × page size. Ideally, the working set of each process is stored in the TLB; otherwise there is a high degree of page faults. Options: increase the page size (may increase fragmentation), or provide multiple page sizes.

TLB Reach — lượng bộ nhớ truy cập được từ TLB — bằng kích thước TLB × kích thước page. Lý tưởng nhất, working set của mỗi tiến trình được chứa trọn trong TLB; nếu không sẽ có tỉ lệ page fault cao. Lựa chọn: tăng page size (có thể tăng fragmentation), hoặc cung cấp nhiều kích thước page khác nhau.
🔍
Ví dụ đời thườngTLB reach giống tầm quan sát của 1 camera an ninh — camera độ phân giải cao (nhiều entry × page lớn) bao quát được nhiều khu vực hơn, giảm số lần phải cử người đi kiểm tra tận nơi (page-table walk).

5Program Structure & I/O Interlock

Program structure affects the number of page faults — consider int[128,128] data, each row stored in one page. Program 1 (loops j outer, i inner) causes 16,384 page faults (128×128); Program 2 (loops i outer, j inner) causes just 128 — accessing memory in row-major order matches how the data is actually laid out in pages.

Cấu trúc chương trình ảnh hưởng tới số page fault — xét int[128,128] data, mỗi hàng nằm trong 1 trang. Chương trình 1 (vòng j ngoài, i trong) gây 16.384 page fault (128×128); Chương trình 2 (vòng i ngoài, j trong) chỉ gây 128 — truy cập bộ nhớ theo đúng thứ tự hàng khớp với cách dữ liệu thực sự được xếp trang.
📖
Ví dụ đời thườngGiống đọc sách: đọc tuần tự từng trang theo thứ tự (Program 2) mượt mà hơn nhiều so với nhảy lung tung lật qua lật lại cả 128 trang cho mỗi dòng (Program 1) — dù tổng lượng chữ đọc được là như nhau.

I/O Interlock — pages must sometimes be locked into memory. Consider I/O: pages used for copying a file from a device must be locked from being selected for eviction by a page-replacement algorithm. Pinning of pages locks them into memory.

I/O Interlock — các trang đôi khi phải bị khóa trong bộ nhớ. Xét trường hợp I/O: các trang dùng để copy 1 file từ thiết bị phải bị khóa, không cho thuật toán page-replacement chọn để đuổi ra. Pinning trang là cách khóa chúng lại trong bộ nhớ.

6Memory Compression: thay thế cho swapping

An alternative to paging is memory compression: rather than paging out modified frames to swap space, the system compresses several frames into a single frame, enabling it to reduce memory usage without resorting to swapping pages at all.

1 giải pháp thay thế cho paging là memory compression: thay vì page out các frame đã sửa ra swap space, hệ thống nén nhiều frame thành 1 frame duy nhất, giúp giảm lượng bộ nhớ dùng mà hoàn toàn không cần swap trang ra ngoài.

Thay vào đó: nén 3 trong số đó (vd 15, 3, 35) và lưu bản nén trong 1 page frame duy nhất ở compressed-frame list — trang 26 vẫn ở modified-frame list, chờ xử lý riêng.

Memory compression là kỹ thuật thay thế cho paging, đặc biệt hữu ích trên mobile systems vốn không hỗ trợ swapping đầy đủ (do hạn chế của flash memory).

How Windows puts all these ideas together

Windows kết hợp tất cả các ý tưởng trên ra sao trong thực tế

Windows is the operating-system example this chapter's slide deck focuses on — and it uses demand paging, working-set bounds, and automatic trimming, echoing nearly every concept covered so far.

Windows là ví dụ hệ điều hành mà bộ slide chương này tập trung vào — và nó dùng demand paging, giới hạn working set, và tự động trimming, gần như lặp lại mọi khái niệm đã học ở các tab trước.

1Demand Paging with Clustering

Windows uses demand paging with clustering. Clustering brings in pages surrounding the faulting page — not just the single page that caused the fault.

Windows dùng demand paging kèm clustering. Clustering nạp vào luôn các trang lân cận trang gây fault — không chỉ đúng 1 trang gây ra fault đó.

2Working Set Minimum / Maximum & Trimming

Processes are assigned a working set minimum and working set maximum. Working set minimum is the minimum number of pages the process is guaranteed to have in memory; a process may be assigned as many pages as it needs up to its working set maximum.

Mỗi tiến trình được gán 1 working set minimum và working set maximum. Working set minimum là số trang tối thiểu mà tiến trình được đảm bảo có trong bộ nhớ; 1 tiến trình có thể được cấp tối đa tới working set maximum của nó.

When the amount of free memory in the system falls below a threshold, automatic working set trimming is performed to restore the amount of free memory. Working set trimming removes pages from processes that have pages in excess of their working set minimum.

Khi lượng bộ nhớ trống trong hệ thống tụt xuống dưới 1 ngưỡng, automatic working set trimming được thực hiện để khôi phục lượng bộ nhớ trống. Working set trimming gỡ bớt trang khỏi những tiến trình đang có nhiều hơn working set minimum của chúng.
