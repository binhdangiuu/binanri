More cores, more problems (for the programmer)

Nhiều nhân hơn, nhiều vấn đề hơn (cho người lập trình)

Multicore or multiprocessor systems put real pressure on programmers, who now have to think in parallel instead of in a straight line.

Hệ đa nhân hay đa xử lý đặt áp lực thật sự lên lập trình viên, giờ phải nghĩ theo hướng song song thay vì theo 1 đường thẳng.

Multicore programming brings five recurring challenges.

Lập trình đa nhân mang lại 5 thách thức hay lặp lại.
🔪 Dividing activities

⚖️ Balance

✂️ Data splitting

🔗 Data dependency

🐞 Testing & debugging

Parallelism implies a system can perform more than one task simultaneously — this genuinely requires multiple cores. Concurrency only supports more than one task making progress; on a single processor/core, the scheduler provides concurrency by rapidly switching between tasks, creating the illusion of simultaneity without ever truly running two things at once.

Parallelism (song song) ngụ ý hệ thống có thể thực hiện hơn 1 tác vụ cùng lúc — điều này thực sự cần nhiều nhân. Concurrency (đồng thời) chỉ hỗ trợ hơn 1 tác vụ cùng tiến triển; trên 1 CPU/nhân duy nhất, scheduler tạo ra concurrency bằng cách chuyển đổi nhanh giữa các tác vụ, tạo ảo giác đồng thời chứ không thực sự chạy 2 việc cùng lúc.

There are two types of parallelism: Data parallelism and Task parallelism.

Có 2 loại parallelism: Data parallelism và Task parallelism.
Data parallelism

Cùng 1 phép toán op, chia dữ liệu ra nhiều nhân.

Task parallelism

Mỗi thread làm 1 việc khác nhau, trên cùng dữ liệu.

Amdahl's Law identifies the speedup from adding cores to an app with serial portion S: speedup ≤ 1 / (S + (1-S)/N). As N → ∞, speedup caps at 1/S — the serial portion has a disproportionate effect on gains.

Định luật Amdahl xác định tốc độ tăng khi thêm nhân vào 1 ứng dụng có phần tuần tự S: speedup ≤ 1 / (S + (1-S)/N). Khi N → ∞, tốc độ tăng chạm trần 1/S — phần tuần tự ảnh hưởng không cân xứng lên mức tăng đạt được.

03 · Mapping

User threads meet kernel threads

Thread cấp người dùng gặp thread cấp kernel

User threads are managed by a user-level threads library — think POSIX Pthreads, Windows threads, Java threads. Kernel threads are supported directly by the kernel, in virtually every general-purpose OS (Windows, Linux, macOS, iOS, Android). The question this section answers: how do the two get mapped onto each other?

Thread cấp người dùng được quản lý bởi 1 thư viện thread cấp người dùng — như POSIX Pthreads, Windows threads, Java threads. Thread cấp kernel được chính kernel hỗ trợ trực tiếp, trong hầu như mọi OS đa dụng (Windows, Linux, macOS, iOS, Android). Câu hỏi phần này trả lời: 2 loại đó được ánh xạ vào nhau ra sao?

In the Many-to-One model, many user-level threads map to a single kernel thread. If one thread makes a blocking system call, the entire process blocks — and because only one thread may ever be in the kernel at a time, multiple threads can never truly run in parallel on a multicore system. Few systems use this today; examples include Solaris Green Threads and GNU Portable Threads.

Trong mô hình Many-to-One, nhiều thread cấp người dùng ánh xạ vào 1 thread kernel duy nhất. Nếu 1 thread gọi system call blocking, cả tiến trình bị chặn — và vì chỉ 1 thread được ở trong kernel tại 1 thời điểm, nhiều thread không bao giờ thực sự chạy song song được trên hệ đa nhân. Ít hệ thống dùng mô hình này ngày nay; ví dụ gồm Solaris Green Threads và GNU Portable Threads.

In the One-to-One model, each user-level thread maps to its own kernel thread — creating a user thread creates a kernel thread. This gives more concurrency than many-to-one, but the number of threads per process is sometimes restricted due to the overhead of managing that many kernel threads. Examples: Windows, Linux.

Trong mô hình One-to-One, mỗi thread cấp người dùng ánh xạ vào chính thread kernel riêng của nó — tạo 1 thread người dùng thì tạo luôn 1 thread kernel. Cho concurrency cao hơn many-to-one, nhưng số thread mỗi process đôi khi bị giới hạn vì overhead quản lý nhiều thread kernel như vậy. Ví dụ: Windows, Linux.

The Many-to-Many model allows many user-level threads to be mapped to many kernel threads — the OS creates as many kernel threads as it judges sufficient. Windows offered this at one point with its ThreadFiber package, but otherwise it isn't very common. A close variant, the Two-level model, works like many-to-many except it additionally allows one specific user thread to be bound directly to its own kernel thread.

Mô hình Many-to-Many cho phép nhiều thread cấp người dùng ánh xạ vào nhiều thread kernel — OS tạo ra số thread kernel mà nó cho là đủ. Windows từng có mô hình này qua gói ThreadFiber, nhưng ngoài ra không phổ biến lắm. 1 biến thể gần giống, mô hình Two-level, hoạt động như many-to-many nhưng còn cho phép 1 thread người dùng cụ thể được gắn trực tiếp (bound) vào thread kernel riêng của nó.
Many-to-Many

4 user thread → 2 kernel thread, ánh xạ linh hoạt.

Two-level

Giống many-to-many, cộng thêm 1 user thread được "bound" riêng 1:1.

Both Many-to-Many and Two-level need real user/kernel communication to keep the right number of kernel threads allocated. They use an intermediate structure, the lightweight process (LWP) — a virtual processor a user thread can be scheduled onto, each attached to one kernel thread.

Cả Many-to-Many và Two-level đều cần giao tiếp user/kernel thật sự để duy trì đúng số thread kernel. Chúng dùng 1 cấu trúc trung gian, lightweight process (LWP) — 1 bộ xử lý ảo mà user thread có thể lập lịch lên đó, mỗi LWP gắn với 1 kernel thread.

04 · APIs

Three ways to actually write threaded code

3 cách để thực sự viết code đa luồng

A thread library gives programmers an API to create/manage threads — implemented in user space, or as a kernel-level library.

1 thread library cho lập trình viên API để tạo/quản lý thread — cài đặt ở user space, hoặc là kernel-level library.

Pthreads is a POSIX standard (IEEE 1003.1c) API — a specification, not an implementation: it only specifies behavior, and it's up to the library developer to actually implement it. Common on UNIX (Linux & macOS).

Pthreads là 1 API chuẩn POSIX (IEEE 1003.1c) — 1 đặc tả (specification), không phải cài đặt (implementation): chỉ quy định hành vi, còn ai phát triển library mới thực sự cài đặt nó. Phổ biến trên UNIX (Linux & macOS).
Asynchronous threading

Cha, con chạy độc lập — hợp cho UI đáp ứng nhanh.

Synchronous threading

Cha CHỜ con — thường để gộp kết quả từ con.

The core Pthreads calls always travel together: pthread_create() spins up a new thread running a given function; pthread_join() makes the parent wait for it; pthread_exit() is what the child calls to end itself.

Bộ lời gọi Pthreads cốt lõi luôn đi cùng nhau: pthread_create() dựng 1 thread mới chạy 1 hàm cho trước; pthread_join() khiến cha chờ nó; pthread_exit() là thứ con gọi để tự kết thúc.

/* Pthreads — create and join */ #include <pthread.h> int sum; /* shared by thread(s) */ void *runner(void *param) { int upper = atoi(param); sum = 0; for (int i = 1; i <= upper; i++) sum += i; pthread_exit(0); } int main(int argc, char *argv[]) { pthread_t tid; pthread_attr_t attr; pthread_attr_init(&attr); pthread_create(&tid, &attr, runner, argv[1]); pthread_join(tid, NULL); printf("sum = %d\n", sum); }

Since the single void* argument can't carry much, real data is usually passed via a small struct pointer instead.

Vì đối số void* duy nhất không tải được nhiều, dữ liệu thật thường được truyền qua 1 con trỏ struct nhỏ thay vào đó.
/* Passing data to threads via a struct */ struct char_print_parms { char character; int count; }; pthread_t thread1_id; struct char_print_parms thread1_args; thread1_args.character = 'A'; thread1_args.count = 100; pthread_create(&thread1_id, NULL, &char_print, &thread1_args);

On Windows, the same job is done by CreateThread() + WaitForSingleObject() — the same wait call already seen for processes in Chapter 3.

Bên Windows, việc tương tự làm bằng CreateThread() + WaitForSingleObject() — đúng lời gọi chờ đã thấy với process ở Chương 3.
/* Windows Multithreaded C Program */ DWORD Sum; /* data shared by threads */ DWORD WINAPI Summation(LPVOID Param) { DWORD Upper = *(DWORD*)Param; for (DWORD i = 1; i <= Upper; i++) Sum += i; return 0; } int main(int argc, char *argv[]) { DWORD ThreadId; HANDLE ThreadHandle; int Param = atoi(argv[1]); ThreadHandle = CreateThread( NULL, 0, Summation, &Param, 0, &ThreadId); WaitForSingleObject(ThreadHandle, INFINITE); CloseHandle(ThreadHandle); printf("sum = %d\n", Sum); }

Java threads are managed by the JVM. Standard practice: implement Runnable rather than extend Thread (keeps the class free to extend something else); wait on it with join().

Java threads do JVM quản lý. Thông lệ chuẩn: implement Runnable thay vì extend Thread (để lớp còn rảnh kế thừa thứ khác); chờ bằng join().
// Implementing Runnable, creating & waiting class Sum implements Runnable { public void run() { int total = 0; for (int i = 1; i <= upper; i++) total += i; System.out.println("sum = " + total); } } Thread worker = new Thread(new Sum()); worker.start(); worker.join(); // waiting on the thread

Java also lets you skip raw Thread objects entirely: submit tasks to an Executor, and it decides how/when they run.

Java cũng cho bỏ qua đối tượng Thread thô hoàn toàn: nộp tác vụ cho 1 Executor, nó tự quyết định chạy ra sao/khi nào.
// Java Executor Framework ExecutorService pool = Executors.newCachedThreadPool(); pool.execute(new Sum()); // submit a Runnable task pool.shutdown(); // no new tasks accepted
Mẹo thi Ghi nhớ 3 lời gọi Pthreads đi cùng nhau: pthread_create() (tạo), pthread_join() (cha chờ con), pthread_exit() (con tự kết thúc) — song song với join() trong Java và WaitForSingleObject() trong Windows.

05 · Automation

Let the compiler manage the threads

Để trình biên dịch tự quản lý thread

As thread counts grow, program correctness gets harder with explicit threading. Implicit threading pushes the creation and management of threads onto compilers and run-time libraries instead of programmers.

Khi số lượng thread tăng, tính đúng đắn của chương trình càng khó với threading tường minh. Implicit threading đẩy việc tạo và quản lý thread cho trình biên dịch và thư viện run-time, thay vì lập trình viên.

Thread pools create threads at start-up; they sit and wait for work. Faster than creating new ones each time, and caps the app's total thread count. Windows API and Java's Executors (fixed/cached/single-thread factories) support this directly.

Thread pool tạo sẵn thread lúc khởi động; chúng ngồi chờ có việc. Nhanh hơn tạo mới mỗi lần, và giới hạn tổng số thread của app. Windows API và Executors của Java (fixed/cached/single-thread) hỗ trợ trực tiếp.
// Java thread pool factory methods (Executors class) ExecutorService fixedPool = Executors.newFixedThreadPool(4); ExecutorService cachedPool = Executors.newCachedThreadPool(); ExecutorService singlePool = Executors.newSingleThreadExecutor();

In Fork-Join parallelism, a task recursively splits itself in half (fork) until pieces are small enough to compute directly, then joins the partial results back together going up the recursion.

Trong Fork-Join parallelism, 1 tác vụ đệ quy chia đôi chính nó (fork) tới khi mảnh đủ nhỏ để tính trực tiếp, rồi join kết quả từng phần lại khi đi ngược lên đệ quy.

OpenMP is compiler directives + API for C/C++/FORTRAN, for shared-memory parallel programming. #pragma omp parallel creates as many threads as there are cores.

OpenMP là chỉ thị biên dịch + API cho C/C++/FORTRAN, cho lập trình song song shared-memory. #pragma omp parallel tạo ra số thread bằng đúng số nhân có sẵn.
/* OpenMP — run this for loop in parallel */ #pragma omp parallel for for (int i = 0; i < N; i++) { c[i] = a[i] + b[i]; }

Grand Central Dispatch (GCD) — Apple's tech for macOS/iOS — manages threading for the programmer. A unit of work is a block, written ^{ ... }.

Grand Central Dispatch (GCD) — công nghệ Apple cho macOS/iOS — tự quản lý threading cho lập trình viên. 1 đơn vị công việc là 1 block, viết dạng ^{ ... }.

Blocks are placed on a dispatch queue: serial queues run blocks one at a time (FIFO); concurrent queues may run several at once.

Block được đặt vào 1 dispatch queue: queue serial chạy từng block 1 (FIFO); queue concurrent có thể chạy nhiều block cùng lúc.

One serial queue is special: the per-process main queue — programmers can create additional serial queues alongside it. Concurrent queues, meanwhile, are provided by the system: four of them, divided by quality of service (QoS).

1 serial queue đặc biệt: main queue của mỗi process — lập trình viên có thể tạo thêm serial queue khác bên cạnh nó. Còn concurrent queue thì do hệ thống cung cấp sẵn: có 4 hàng, chia theo quality of service (QoS).

QOS_CLASS_USER_INITIATED

QOS_CLASS_USER_UTILITY

Việc chạy lâu hơn, không cần xong ngay (vd tải file).

QOS_CLASS_USER_BACKGROUND

Việc người dùng không thấy (vd đánh index, sao lưu).

Swift's equivalent unit of work is a closure — like a block, minus the caret — submitted via dispatch_async().

Bên Swift, đơn vị công việc tương đương là 1 closure — giống block, trừ dấu mũ — nộp qua dispatch_async().
// Swift closure submitted to a queue queue.async { print("hi from a closure") }

Finally, Intel Threading Building Blocks (TBB) is a C++ template library — a serial for loop becomes parallel_for, and the library decides how to split the range across cores.

Cuối cùng, Intel Threading Building Blocks (TBB) là 1 thư viện template C++ — vòng lặp for tuần tự trở thành parallel_for, thư viện tự quyết định cách chia khoảng lặp ra các nhân.
// serial version for (int i = 0; i < n; i++) apply(v[i]); // same loop with Intel TBB parallel_for(size_t(0), n, [=](size_t i) { apply(v[i]); });
Mẹo thi 5 kỹ thuật implicit threading cần nhớ tên: Thread Pools, Fork-Join, OpenMP, Grand Central Dispatch, Intel TBB. Điểm chung: LẬP TRÌNH VIÊN không tự tạo/quản lý thread tường minh — compiler/run-time library lo việc đó.

06 · Gotchas

Where multithreading gets genuinely tricky

Chỗ đa luồng thực sự trở nên rắc rối

Five recurring issues show up once threads enter the picture: fork()/exec() semantics, signal handling, thread cancellation, thread-local storage, and scheduler activations.

5 vấn đề hay lặp lại xuất hiện ngay khi thread bước vào bức tranh: ngữ nghĩa fork()/exec(), xử lý signal, hủy thread, thread-local storage, và scheduler activations.

The first question is subtle: does fork() duplicate only the calling thread, or every thread? Some UNIXes provide both versions. exec() works as normal — it replaces the whole process, all threads included, with the new program.

Câu hỏi đầu tiên khá tinh tế: fork() chỉ nhân bản thread đang gọi, hay mọi thread? Vài UNIX cung cấp cả 2 phiên bản. exec() hoạt động bình thường — thay thế cả process, kể cả mọi thread, bằng chương trình mới.
fork() — chỉ nhân bản thread gọi nó
fork() — nhân bản TẤT CẢ thread

Signals notify a process an event occurred, handled by a default or user-defined handler.

Signal báo cho process biết 1 sự kiện đã xảy ra, xử lý bởi handler mặc định hoặc do người dùng định nghĩa.
📶

In a multithreaded process, though, where should a signal actually go?

Nhưng trong process đa luồng, signal thật sự nên đi đâu?
1. Đúng thread liên quan

Chỉ thread mà signal thực sự áp dụng mới nhận.

2. Mọi thread

Gửi broadcast tới toàn bộ thread trong process.

3. Một số thread

Chỉ định 1 tập con thread cụ thể nhận.

4. Thread chuyên trách

1 thread riêng được gán nhận TẤT CẢ signal của process.

Thread cancellation terminates a target thread before it finishes.

Thread cancellation kết thúc 1 target thread trước khi nó chạy xong.

Asynchronous cancellation kills it immediately; deferred (the default) lets it check periodically and cancel itself at a safe cancellation point (e.g. pthread_testcancel()).

Kiểu asynchronous giết ngay lập tức; kiểu deferred (mặc định) cho thread tự kiểm tra định kỳ và tự hủy ở 1 cancellation point an toàn (vd pthread_testcancel()).

Thread-local storage (TLS) gives each thread its own copy of data — visible across function calls like static data, but unique per thread instead of shared.

Thread-local storage (TLS) cho mỗi thread bản sao dữ liệu riêng — hiển thị xuyên các lần gọi hàm giống static, nhưng riêng theo từng thread thay vì dùng chung.

Finally, Scheduler activations solve the Many-to-Many/Two-level communication problem via upcalls: the kernel proactively tells the thread library when something needs a reaction, like a kernel thread about to block.

Cuối cùng, Scheduler activations giải quyết vấn đề giao tiếp của Many-to-Many/Two-level qua upcall: kernel chủ động báo cho thread library khi có gì cần phản ứng, như 1 thread kernel sắp block.
Mẹo thi Nhớ default của Pthreads cancellation là DEFERRED, không phải asynchronous — thread chỉ thực sự bị hủy khi chạm cancellation point (vd pthread_testcancel()). Đừng nhầm TLS với biến static: TLS riêng theo TỪNG thread, static dùng chung.

How Windows and Linux actually implement threads

Windows và Linux thực sự cài đặt thread ra sao

Both take a one-to-one, kernel-level approach — but structure the underlying data very differently.

Cả hai đều theo cách tiếp cận one-to-one, cấp kernel — nhưng cấu trúc dữ liệu bên dưới rất khác nhau.

The Windows API implements one-to-one mapping — every user thread gets its own kernel thread.

Windows API cài đặt ánh xạ one-to-one — mỗi user thread có 1 kernel thread riêng của nó.

Each thread carries a thread id and a register set, plus separate user-mode and kernel-mode stacks depending on which mode it's running in.

Mỗi thread mang 1 thread id và 1 tập thanh ghi, cộng thêm stack chế độ người dùng và chế độ kernel riêng biệt tùy đang chạy ở chế độ nào.

It also gets a private data storage area for run-time libraries and DLLs. All of this together — registers, stacks, private storage — is the thread's context.

Nó còn có 1 vùng lưu trữ dữ liệu riêng cho thư viện run-time và DLL. Tất cả gộp lại — thanh ghi, stack, vùng lưu trữ riêng — chính là context của thread.

On Linux, threads are called tasks, created via clone() — controlled by flags deciding exactly what's shared with the parent.

Trên Linux, thread gọi là task, tạo qua clone() — điều khiển bởi flag quyết định chính xác cái gì được chia sẻ với cha.
