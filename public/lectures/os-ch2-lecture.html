01 · Services

What does an OS actually promise?

OS thực sự hứa hẹn điều gì?

Every service below exists to answer one of two questions: "does this make life easier for the person/program using the machine?" or "does this keep the machine itself running well for everyone sharing it?"

Mỗi dịch vụ dưới đây tồn tại để trả lời 1 trong 2 câu hỏi: "cái này có làm cuộc sống người/chương trình dùng máy dễ hơn không?", hay "cái này có giúp chính cái máy chạy tốt cho mọi người đang dùng chung không?"
Before the list — take a guess: when you double-click a file to open it, how many separate "services" does the OS quietly perform before you see anything on screen? Trước khi xem danh sách — thử đoán: khi bạn nhấp đúp vào 1 file để mở, OS âm thầm thực hiện bao nhiêu "dịch vụ" riêng biệt trước khi bạn thấy gì đó hiện lên màn hình?

Operating systems provide an environment for the execution of programs and offer services to both programs and users. One group of these services exists purely to make life easier for the person at the keyboard — Silberschatz calls this the user interface (UI) group.

Hệ điều hành tạo ra môi trường để chương trình chạy, và cung cấp dịch vụ cho cả chương trình lẫn người dùng. Một nhóm dịch vụ tồn tại chỉ để giúp cuộc sống của người ngồi trước bàn phím dễ dàng hơn — Silberschatz gọi nhóm này là giao diện người dùng (UI).
🗺️
The big pictureUsers & other system programs sit on top; they reach "operating system services" through a user interface, and everything below that line is the OS itself, sitting on hardware.

The UI itself can be a Command-Line Interface (CLI), a Graphical User Interface (GUI), or a touch-screen — the next tab digs into all three. Beyond just showing a prompt, the OS also handles program execution: loading a program into memory, running it, and ending it — either normally, or abnormally when an error occurs.

UI có thể là giao diện dòng lệnh (CLI), giao diện đồ họa (GUI), hoặc màn hình cảm ứng — tab kế tiếp sẽ đi sâu vào cả 3. Ngoài việc hiện dấu nhắc lệnh, OS còn lo thực thi chương trình: nạp chương trình vào bộ nhớ, chạy nó, rồi kết thúc — kết thúc bình thường, hoặc bất thường khi có lỗi.
🖥️
Program execution, 3 trạng tháiload vào bộ nhớ → run → end (bình thường hoặc bất thường khi lỗi).

I/O operations come next: a running program may need to read/write a file or talk to a device, and a user typically can't control I/O hardware directly for protection and efficiency reasons — so the OS must provide a way to do it. Closely related is file-system manipulation: programs need to read, write, create, delete, search files and directories, list information about them, and manage permissions.

Các thao tác I/O tiếp theo: chương trình đang chạy có thể cần đọc/ghi file hoặc nói chuyện với thiết bị, mà người dùng thường không được điều khiển trực tiếp phần cứng I/O vì lý do bảo vệ và hiệu năng — nên OS phải cung cấp cách làm việc đó. Liên quan chặt là thao tác trên hệ thống file: chương trình cần đọc, ghi, tạo, xóa, tìm kiếm file/thư mục, liệt kê thông tin, và quản lý quyền truy cập.
📁
I/O & file-system callsread, write, open, close, delete, search — luôn đi qua OS, không bao giờ chạm trực tiếp phần cứng.

Processes often need to exchange information — with each other on the same machine, or across a network — which is what communications services provide, via either shared memory or message passing (packets moved by the OS itself). And because things do go wrong, the OS needs constant error detection across CPU, memory, hardware, I/O devices, and user programs, taking the right corrective action each time.

Các tiến trình thường cần trao đổi thông tin — với nhau trên cùng máy, hoặc qua mạng — đó là việc của dịch vụ giao tiếp (communications), qua bộ nhớ dùng chung hoặc truyền thông điệp (gói tin do chính OS di chuyển). Và vì sự cố luôn xảy ra, OS cần liên tục phát hiện lỗi ở CPU, bộ nhớ, phần cứng, thiết bị I/O, và cả chương trình người dùng, rồi có hành động sửa lỗi phù hợp mỗi lần.

A second group of services exists purely for the system's own efficient operation via resource sharing. Resource allocation assigns CPU cycles, memory, storage, and I/O devices fairly when multiple users or jobs run at once. Logging (also called accounting) tracks which users consume how much of which resource — useful for billing or usage statistics.

Nhóm thứ hai tồn tại chỉ để chính hệ thống vận hành hiệu quả, thông qua việc chia sẻ tài nguyên. Cấp phát tài nguyên phân chia chu kỳ CPU, bộ nhớ, lưu trữ, thiết bị I/O công bằng khi nhiều người dùng/job chạy cùng lúc. Ghi log (còn gọi accounting) theo dõi ai dùng bao nhiêu tài nguyên nào — hữu ích để tính phí hoặc thống kê sử dụng.
⚖️
Resource allocation vs Loggingchia tài nguyên công bằng cho ai đang cần → rồi ghi lại ai đã dùng bao nhiêu.

Finally, Protection ensures all access to system resources is controlled so concurrent processes don't interfere with each other, while Security defends the system from outsiders through user authentication, extending even to protecting external I/O devices from invalid access attempts.

Cuối cùng, bảo vệ (Protection) đảm bảo mọi quyền truy cập tài nguyên hệ thống đều được kiểm soát để các tiến trình chạy song song không đụng nhau, còn an ninh (Security) bảo vệ hệ thống khỏi người ngoài qua việc xác thực người dùng, và mở rộng ra cả việc bảo vệ thiết bị I/O bên ngoài khỏi những lần truy cập trái phép.
🔒
Protection vs SecurityProtection = chặn tiến trình này đụng tiến trình kia; Security = chặn kẻ ngoài đột nhập.

02 · Interface

Three doorways into the same services

Ba cánh cửa dẫn tới cùng 1 tập dịch vụ

CLI, GUI, and touch are just different skins over the exact same underlying OS services from the last tab — none of them is "more powerful," they just fit different hands and different devices.

CLI, GUI, và cảm ứng chỉ là những lớp vỏ khác nhau phủ lên đúng cùng 1 tập dịch vụ OS ở tab trước — không cái nào "mạnh hơn" cái nào, chúng chỉ hợp với những đôi tay và thiết bị khác nhau.

The command interpreter — often called a shell — is what actually implements the Command-Line Interface (CLI). Sometimes it lives inside the kernel; more often it's just a regular system program, and a system may even ship several shells to choose from. Its whole job, over and over, is: fetch a command from the user, execute it.

Trình thông dịch lệnh — hay còn gọi là shell — chính là thứ hiện thực giao diện dòng lệnh (CLI). Đôi khi nó nằm trong kernel; thường thì chỉ là 1 chương trình hệ thống bình thường, và 1 hệ thống còn có thể có sẵn nhiều shell để chọn. Việc của nó, lặp đi lặp lại, chỉ là: lấy 1 lệnh từ người dùng, rồi thực thi nó.
bash-4.4$ ls -l notes.txt
-rw-r--r-- 1 binh binh 214 Aug 20 notes.txt
bash-4.4$ cat notes.txt
ôn tập chương 2...

Commands are sometimes built directly into the shell; other times a command is just the name of a separate program the shell finds and runs. That second design is nice because adding a whole new feature can be as simple as writing a new program — no need to touch the shell itself.

Có khi lệnh được cài sẵn ngay trong shell; có khi lệnh chỉ là tên của 1 chương trình riêng mà shell tìm rồi chạy. Cách thiết kế thứ hai hay ở chỗ: muốn thêm hẳn 1 tính năng mới chỉ cần viết thêm 1 chương trình mới — không cần đụng vào chính shell.
🧩
Built-in vs. separate programlệnh cài sẵn trong shell, hay chỉ là tên 1 chương trình rời mà shell tìm rồi chạy.

The Graphical User Interface (GUI) gives a friendlier, mouse-driven desktop metaphor: icons represent files, programs, and actions, and various mouse clicks trigger information, run actions, or open directories. First invented at Xerox PARC in the 1970s, it's now the default on almost everything.

Giao diện đồ họa (GUI) mang lại ẩn dụ desktop thân thiện, điều khiển bằng chuột: icon đại diện cho file, chương trình, hành động, và các cú nhấp chuột khác nhau sẽ hiện thông tin, chạy hành động, hoặc mở thư mục. Được phát minh lần đầu tại Xerox PARC vào thập niên 1970, giờ đây nó là mặc định ở hầu hết mọi nơi.

Thiết bị màn hình cảm ứng cần hẳn 1 kiểu giao diện thứ tư, vì chuột không khả thi cũng không cần thiết: hành động và lựa chọn giờ dựa trên cử chỉ (gesture), bàn phím ảo hiện ngay trên màn hình để nhập chữ, và nhiều hệ thống còn thêm cả ra lệnh bằng giọng nói lên trên tất cả.

Most systems today actually include both CLI and GUI interfaces at once. Microsoft Windows is GUI-first but ships a "command" shell alongside it; Apple's macOS is an "Aqua" GUI sitting on top of a Unix kernel, with full shell access underneath; Unix and Linux offer CLI by default with optional GUI environments like CDE, KDE, or GNOME layered on top.

Hầu hết hệ thống ngày nay thực ra có cả CLI lẫn GUI cùng lúc. Microsoft Windows lấy GUI làm chính nhưng vẫn kèm 1 shell "command" đi cùng; macOS của Apple là GUI "Aqua" nằm trên nhân Unix, bên dưới vẫn truy cập được shell đầy đủ; Unix và Linux mặc định dùng CLI, có thể lắp thêm môi trường GUI tùy chọn như CDE, KDE, hay GNOME.

03 · Mechanism

The only legal doorway into the kernel

Cánh cửa hợp pháp duy nhất vào kernel

Every service from tab 1 — reading a file, allocating memory, talking to a device — ultimately has to cross the user/kernel boundary from Chapter 1. A system call is that crossing point, and nothing else.

Mọi dịch vụ ở tab 1 — đọc file, cấp phát bộ nhớ, nói chuyện với thiết bị — cuối cùng đều phải băng qua ranh giới user/kernel đã học ở Chương 1. System call chính là điểm băng qua đó, không hơn không kém.

A system call is the programming interface to the services the OS provides, typically written in a high-level language like C or C++. Programs mostly don't invoke system calls directly — instead they go through a high-level Application Programming Interface (API). The three most common are Win32 API for Windows, POSIX API for virtually all UNIX, Linux, and Mac OS X systems, and Java API for programs running on the JVM.

System call là giao diện lập trình tới các dịch vụ mà OS cung cấp, thường viết bằng ngôn ngữ bậc cao như C hoặc C++. Chương trình phần lớn không gọi system call trực tiếp — mà đi qua 1 Giao diện lập trình ứng dụng (API) bậc cao. 3 API phổ biến nhất: Win32 API cho Windows, POSIX API cho hầu hết mọi hệ UNIX, Linux, Mac OS X, và Java API cho chương trình chạy trên JVM.

To see this concretely, walk through the system call sequence needed just to copy the contents of one file into another — far more steps than the one line of code a programmer actually writes:

Để thấy rõ điều này, hãy xem qua chuỗi system call cần thiết chỉ để copy nội dung từ file này sang file khác — nhiều bước hơn hẳn so với 1 dòng code mà lập trình viên thực sự viết ra:
Acquire input file name → prompt on screen → accept from keyboard
Acquire output file name → prompt on screen → accept from keyboard

Underneath one call like open() sits the system-call interface: an index table indexed by a number associated with each system call, which invokes the intended call inside the kernel and returns its status plus any return values. The caller only needs to obey the API and understand what the OS will do — it needs to know nothing about how the call is actually implemented, since that detail is hidden away and managed by a run-time support library built into the compiler's libraries.

Bên dưới 1 lời gọi như open() là giao diện system call: 1 bảng được đánh chỉ số theo 1 con số gắn với từng system call, dùng để gọi đúng lời gọi trong kernel và trả về trạng thái cùng giá trị trả về (nếu có). Bên gọi chỉ cần tuân theo API và hiểu OS sẽ làm gì — không cần biết gì về cách lời gọi được cài đặt thật sự, vì chi tiết đó được giấu đi và quản lý bởi 1 thư viện hỗ trợ runtime tích hợp sẵn trong thư viện của trình biên dịch.
📇
API–System call–OS relationshipuser application gọi open() → hệ thống tra "index table" tìm đúng cài đặt open() → nhảy vào kernel thực thi → trả kết quả ngược lại cho ứng dụng.
Why hide the implementation at all? Because the OS team can completely rewrite how open() works internally — new file system, new algorithm — and every program that ever called open() keeps working, unmodified. Vì đội ngũ phát triển OS có thể viết lại hoàn toàn cách open() hoạt động bên trong — hệ thống file mới, thuật toán mới — mà mọi chương trình từng gọi open() vẫn chạy tốt, không cần sửa gì cả.

When a system call needs more information than just "which call is this," that extra data has to be passed somehow. Three general methods exist. The simplest is passing parameters in registers — but registers may not be enough if there are more parameters than available registers.

Khi 1 system call cần nhiều thông tin hơn chỉ là "đây là lời gọi nào," dữ liệu thêm đó phải được truyền đi bằng cách nào đó. Có 3 cách chung. Cách đơn giản nhất là truyền tham số qua thanh ghi (registers) — nhưng thanh ghi có thể không đủ nếu số tham số nhiều hơn số thanh ghi có sẵn.
Method 1

Registers

  • Fastest, simplest
  • Limited by register count
Method 2

A block/table in memory

  • Address of block passed in a register
  • Used by Linux & Solaris
Method 3

Push onto the stack

  • Program pushes, OS pops
  • No limit on count or length

Parameters can also be stored in a block, or table, in memory, with the address of that block passed as a single parameter in a register — the approach taken by Linux and Solaris. Finally, parameters can be pushed onto the stack by the program and popped off by the OS; neither the block nor the stack method limits the number or length of parameters being passed.

Tham số cũng có thể được lưu trong 1 khối (block), hay bảng, trong bộ nhớ, với địa chỉ của khối đó được truyền như 1 tham số duy nhất qua thanh ghi — cách mà Linux và Solaris dùng. Cuối cùng, tham số có thể được đẩy lên ngăn xếp (stack) bởi chương trình rồi được OS lấy ra; cả cách dùng khối lẫn stack đều không giới hạn số lượng hay độ dài tham số truyền vào.

04 · Catalog

Six categories, two very different operating systems

6 loại system call, 2 hệ điều hành rất khác nhau

Every system call an OS offers falls into one of six buckets. Same buckets, wildly different spelling from one OS to the next — which is exactly why the API layer from the last tab exists.

Mọi system call mà 1 OS cung cấp đều rơi vào 1 trong 6 nhóm. Cùng 6 nhóm đó, nhưng tên hàm cụ thể lại khác nhau hoàn toàn giữa các OS — và đó chính xác là lý do lớp API ở tab trước tồn tại.
Process control

create/terminate process, load, execute, wait for time or event, allocate memory, debugger for bugs, locks for shared data.

File management

create, delete, open, close, read, write, reposition, get/set file attributes.

Device management

request/release a device, read, write, reposition, get/set device attributes, logically attach or detach.

Information maintenance

get/set time or date, get/set system data, get/set process, file, or device attributes.

Communications

create/delete a connection, send/receive messages, transfer status info, attach/detach remote devices.

Protection

control access to resources, get and set permissions, allow and deny user access.

Communication between processes can follow either the message-passing model — exchanging messages via a host name or process name — or the shared-memory model, where processes create and gain access to a common memory region to transfer data directly.

05 · Tooling

What most users actually think "the OS" is

Thứ mà hầu hết người dùng nghĩ chính là "OS"

Ask a random user what their operating system does, and they'll describe a file explorer, a compiler, a background updater — not raw system calls. That's because most people's whole view of the OS is really its system programs.

Hỏi 1 người dùng bất kỳ OS của họ làm gì, họ sẽ mô tả trình quản lý file, trình biên dịch, bộ cập nhật chạy nền — chứ không phải system call thô. Vì cái nhìn của hầu hết mọi người về OS thực ra chính là các chương trình hệ thống của nó.

System programs provide a convenient environment for program development and execution, and they're what defines most users' view of the operating system — not the actual, invisible system calls underneath. They fall into several categories: file manipulation, status information, programming-language support, program loading and execution, communications, background services, and application programs.

Chương trình hệ thống tạo ra môi trường thuận tiện để phát triển và chạy chương trình, và chính chúng mới định hình cái nhìn của hầu hết người dùng về hệ điều hành — chứ không phải các system call vô hình bên dưới. Chúng chia thành vài loại: thao tác file, thông tin trạng thái, hỗ trợ ngôn ngữ lập trình, nạp và chạy chương trình, giao tiếp, dịch vụ nền, và chương trình ứng dụng.
File manipulation

Create, delete, copy, rename, print, list, and generally manipulate files and directories.

Status information

Date, time, free memory/disk space, number of users — sometimes even a settings interface.

Programming-language support

Compilers, assemblers, debuggers, interpreters for common languages, all bundled with the OS.

Program loading & execution

Loaders, linkers, and debuggers for general and language-specific programs.

Communications

Virtual connections between processes, users, and even different computer systems.

Background services

Daemons that launch at boot and keep running in the background, outside the kernel itself.

These background services — commonly called daemons — start when the system boots and keep running quietly for as long as the machine is on. Crucially, most of them run in a regular user context, not inside the kernel: a web server or a print spooler doesn't need kernel privileges to do its job.

Dịch vụ nền — thường gọi là daemon — khởi động khi hệ thống boot và chạy âm thầm suốt thời gian máy còn bật. Điều quan trọng: hầu hết chạy ở ngữ cảnh người dùng bình thường, không nằm trong kernel: 1 web server hay 1 hàng đợi in không cần đặc quyền kernel để làm việc của nó.

One specific pair of system programs deserves a closer look: the linker and the loader. The program then sits on secondary storage as that binary executable, and must be brought into memory by the loader to actually run. Part of that job is relocation: assigning final memory addresses to every part of the program and adjusting its code and data so those addresses match. Modern general-purpose systems mostly skip statically linking libraries into every executable — instead they use dynamically linked libraries (Windows calls them DLLs), loaded only when needed and shared across every program that uses that same library version.

Chương trình sau đó nằm trên bộ nhớ phụ dưới dạng file thực thi nhị phân đó, và phải được loader đưa vào bộ nhớ để thực sự chạy. 1 phần việc của loader là relocation (tái định vị): gán địa chỉ bộ nhớ cuối cùng cho từng phần của chương trình và chỉnh code/dữ liệu để khớp đúng địa chỉ đó. Hệ thống đa dụng hiện đại phần lớn không còn liên kết tĩnh thư viện vào mọi file thực thi — thay vào đó dùng thư viện liên kết động (Windows gọi là DLL), chỉ nạp khi cần và dùng chung cho mọi chương trình dùng cùng phiên bản thư viện đó.

06 · Philosophy

Designing an OS is not a solved problem

Thiết kế OS chưa bao giờ là bài toán có đáp án cố định

There's no single "correct" way to build an operating system — every design starts from a set of goals and specifications, shaped heavily by the hardware chosen and the type of system being built.

Không có 1 cách "đúng duy nhất" để xây 1 hệ điều hành — mọi thiết kế đều bắt đầu từ 1 bộ mục tiêu và đặc tả, bị định hình mạnh bởi phần cứng được chọn và loại hệ thống đang xây.

The very first fork in the road is whose goals come first. User goals ask the system to be convenient to use, easy to learn, reliable, safe, and fast. System goals ask something almost opposite: that the OS be easy to design, implement, and maintain, as well as flexible, reliable, error-free, and efficient.

Ngã rẽ đầu tiên là mục tiêu của ai được ưu tiên trước. Mục tiêu người dùng đòi hỏi hệ thống thuận tiện khi dùng, dễ học, đáng tin cậy, an toàn, và nhanh. Mục tiêu hệ thống đòi hỏi gần như ngược lại: OS phải dễ thiết kế, dễ hiện thực, dễ bảo trì, cùng với linh hoạt, đáng tin cậy, không lỗi, và hiệu quả.
👤 User goals
  • Convenient to use
  • Easy to learn
  • Reliable, safe, fast
⚙️ System goals
  • Easy to design & implement
  • Easy to maintain
  • Flexible, reliable, efficient

Because these goals genuinely pull in different directions, no universal set of specifications satisfies everyone — the same goals mean something completely different for an embedded system with 16 MB of memory and no disk than they do for a general-purpose system juggling many different resources.

Vì các mục tiêu này thực sự kéo về 2 hướng khác nhau, không có bộ đặc tả chung nào làm hài lòng tất cả — cùng 1 mục tiêu lại mang ý nghĩa hoàn toàn khác với 1 hệ thống nhúng chỉ có 16 MB bộ nhớ và không ổ đĩa, so với 1 hệ đa dụng đang phải cân nhiều loại tài nguyên khác nhau cùng lúc.

A second, orthogonal separation matters just as much: policy decides what will be done, while mechanism decides how to do it. Keeping the two separate gives real flexibility — for example, changing a resource-protection timer's length is purely a policy decision, and it should be possible to make that change without ever touching the underlying mechanism that enforces it.

Một sự tách biệt thứ hai, độc lập, cũng quan trọng không kém: policy (chính sách) quyết định cái gì sẽ được làm, còn mechanism (cơ chế) quyết định làm bằng cách nào. Giữ 2 thứ này tách rời mang lại sự linh hoạt thật sự — ví dụ, đổi độ dài của 1 bộ đếm thời gian bảo vệ tài nguyên chỉ là 1 quyết định policy, và việc đổi đó nên thực hiện được mà không cần đụng vào cơ chế đang thực thi nó bên dưới.

Finally, implementation language shapes the whole system. Early OSes were written entirely in assembly language; then came systems like Unix, mostly written in C — a much bigger jump than it sounds, since it made those systems dramatically more portable across hardware. Today, most of an OS's body is still C, with C++ and scripting languages like Perl or Python handling higher-level system programs. The trade-off is real: higher-level code is easier to port and maintain, but it typically runs slower and needs more storage than hand-written assembly.

Cuối cùng, ngôn ngữ hiện thực định hình cả hệ thống. OS đời đầu viết hoàn toàn bằng hợp ngữ (assembly); rồi tới các hệ như Unix, phần lớn viết bằng C — một bước nhảy lớn hơn tưởng tượng, vì nó khiến các hệ này dễ mang đi (portable) hơn hẳn giữa các loại phần cứng. Ngày nay, phần thân của OS vẫn chủ yếu là C, còn C++ và ngôn ngữ kịch bản như Perl hay Python lo phần chương trình hệ thống bậc cao hơn. Đánh đổi là có thật: code bậc cao dễ mang đi và bảo trì hơn, nhưng thường chạy chậm hơn và tốn bộ nhớ hơn so với hợp ngữ viết tay.

07 · Architecture

Five ways to organize one giant program

5 cách tổ chức 1 chương trình khổng lồ

A general-purpose OS is a genuinely huge program. Every design below is really just a different answer to "how do we keep something this big from turning into an unmanageable mess?"

1 OS đa dụng thực sự là 1 chương trình cực lớn. Mỗi thiết kế dưới đây chỉ là 1 câu trả lời khác nhau cho câu hỏi "làm sao giữ cho thứ to thế này không biến thành mớ hỗn độn không quản nổi?"

The simplest structure has no structure at all — think MS-DOS, where the whole system is a large program with barely any internal boundaries. Slightly more organized is the Monolithic structure of the original UNIX, which split into just two separable parts: system programs, and the kernel itself.

Cấu trúc đơn giản nhất là không có cấu trúc gì cả — hãy nghĩ tới MS-DOS, nơi toàn bộ hệ thống chỉ là 1 chương trình lớn gần như không có ranh giới nội bộ nào. Có tổ chức hơn 1 chút là cấu trúc Monolithic (khối liền) của UNIX nguyên bản, chỉ tách ra 2 phần riêng biệt: chương trình hệ thống, và chính kernel.
🧱
MS-DOS: không cấu trúcgần như 1 khối chương trình lớn, ranh giới nội bộ rất mờ nhạt.

That original UNIX kernel consists of everything below the system-call interface and above the physical hardware — providing the file system, CPU scheduling, memory management, and every other OS function, all inside one large function, for one privilege level.

Kernel UNIX nguyên bản đó gồm mọi thứ nằm dưới giao diện system-call và trên phần cứng vật lý — cung cấp hệ thống file, lập lịch CPU, quản lý bộ nhớ, và mọi chức năng OS khác, tất cả gói trong 1 khối chức năng lớn, chạy ở 1 mức đặc quyền duy nhất.

The Layered approach divides the operating system into a number of layers (levels), each built on top of only the layers below it. Layer 0 is the hardware; the highest layer, N, is the user interface. With modularity, every layer is designed to use only the functions (operations) and services of the layers strictly below it — never above, and never skipping around.

Cách tiếp cận phân lớp (Layered) chia hệ điều hành thành nhiều lớp (tầng), mỗi tầng chỉ được xây trên các tầng bên dưới nó. Lớp 0 là phần cứng; lớp cao nhất, N, là giao diện người dùng. Với tính modularity, mỗi lớp được thiết kế để chỉ dùng chức năng (thao tác) và dịch vụ của các lớp nằm ngay bên dưới nó — không bao giờ dùng lớp trên, và không bao giờ nhảy cóc.

Microkernels take the opposite instinct: move as much as possible out of the kernel and into user space, leaving only a minimal core inside — Mach is the classic example, and Mac OS X's kernel (Darwin) is partly based on it. Since the kernel and its user-space modules can no longer just call each other's functions directly, they communicate entirely via a message-passing model instead.

Microkernel đi theo hướng ngược lại: đưa càng nhiều thứ ra khỏi kernel càng tốt, chuyển vào user space, chỉ để lại 1 lõi tối thiểu bên trong — Mach là ví dụ kinh điển, và kernel của Mac OS X (Darwin) 1 phần dựa trên nó. Vì kernel và các module ở user space giờ không thể gọi thẳng hàm của nhau, chúng giao tiếp hoàn toàn qua mô hình truyền thông điệp.

The benefits are real: a microkernel is easier to extend, easier to port to new hardware architectures, and — since less code runs with full kernel privileges — generally more secure and reliable. The detriment is just as real: constantly shuttling messages between user space and kernel space introduces genuine performance overhead compared to just calling a function directly inside one big kernel.

Lợi ích là có thật: microkernel dễ mở rộng hơn, dễ chuyển (port) sang kiến trúc phần cứng mới hơn, và — vì ít code chạy với đặc quyền kernel đầy đủ hơn — nhìn chung an toàn và đáng tin cậy hơn. Bất lợi cũng có thật: việc liên tục chuyển thông điệp qua lại giữa user space và kernel space tạo ra chi phí hiệu năng thật sự, so với việc chỉ gọi thẳng 1 hàm bên trong 1 kernel lớn.
⚡
Đánh đổian toàn hơn, dễ mở rộng hơn — nhưng chậm hơn vì phải nhắn tin qua lại liên tục.

Many modern OSes take a third route: Loadable Kernel Modules (LKMs). The kernel uses an object-oriented approach where each core component is separate, and each talks to the others only through known, well-defined interfaces — every module is loadable into the kernel as needed. It's similar to layers, but noticeably more flexible, since modules can call each other more freely than strict layering allows. Linux and Solaris both use this approach.

Nhiều OS hiện đại đi theo hướng thứ ba: Loadable Kernel Modules (LKM) — module kernel có thể nạp được. Kernel dùng cách tiếp cận hướng đối tượng, mỗi thành phần lõi tách riêng, và mỗi thành phần chỉ nói chuyện với nhau qua giao diện đã biết rõ, được định nghĩa sẵn — mỗi module có thể nạp vào kernel khi cần. Nó giống layer, nhưng linh hoạt hơn rõ rệt, vì các module có thể gọi nhau tự do hơn so với phân lớp nghiêm ngặt. Cả Linux và Solaris đều dùng cách này.
🧩
Loadable Kernel Modulegiống layer, nhưng module có thể cắm vào/rút ra khỏi kernel bất cứ lúc nào cần.

In practice, almost no modern OS is one pure model — most are Hybrid systems mixing several approaches to balance performance, security, and usability. Linux and Solaris are monolithic, plus modular for loading functionality dynamically. Windows is mostly monolithic, plus microkernel behavior for different "subsystem personalities." Apple's macOS is hybrid, layered, using Aqua UI and Cocoa on top — with a kernel underneath combining the Mach microkernel and BSD Unix parts, plus an I/O kit and dynamically loadable kernel extensions.

Trong thực tế, gần như không OS hiện đại nào là 1 mô hình thuần túy — hầu hết là hệ lai (Hybrid), trộn nhiều cách tiếp cận để cân bằng hiệu năng, an ninh, và dễ dùng. Linux và Solaris là monolithic, cộng thêm modular để nạp chức năng động. Windows chủ yếu là monolithic, cộng thêm hành vi microkernel cho các "personality" hệ thống con khác nhau. macOS của Apple là hybrid, phân lớp, dùng Aqua UI và Cocoa ở trên — với kernel bên dưới kết hợp microkernel Mach và các phần BSD Unix, cộng thêm I/O kit và kernel extension nạp được linh động.

macOS and iOS share the same underlying structure, layered from top to bottom: applications sit on a user-experience layer (Aqua on macOS, Cocoa Touch on iOS), which sits on application frameworks, which sit on core frameworks, which finally sit on the kernel environment — Darwin.

Darwin itself is the clean hybrid example: applications sit on a library interface, which splits into Mach traps on one side and BSD (POSIX) system calls on the other — both routes lead into scheduling, IPC, and memory management, plus iokit and kexts (kernel extensions) for hardware, all inside the Mach kernel.

Darwin chính là ví dụ hybrid rõ ràng nhất: ứng dụng nằm trên 1 lớp giao diện thư viện, tách thành 2 nhánh — Mach traps 1 bên và BSD (POSIX) system calls bên kia — cả 2 đều dẫn vào lập lịch, IPC, và quản lý bộ nhớ, cộng thêm iokit và kexts (kernel extension) cho phần cứng, tất cả nằm trong Mach kernel.

iOS is Apple's mobile OS for the iPhone and iPad — structured much like macOS but built for ARM CPUs, and it can't natively run macOS applications. From bottom to top it layers Core OS (the macOS-kernel-based foundation) up through Core Services, then Media Services for graphics/audio/video, capped by Cocoa Touch — the Objective-C API that developers actually write against.

iOS là hệ điều hành di động của Apple cho iPhone và iPad — cấu trúc rất giống macOS nhưng xây cho CPU ARM, và không chạy được ứng dụng macOS gốc. Android, developed largely by Google under the Open Handset Alliance, is a free, open-source, Linux-based mobile platform. Its kernel is a modified Linux kernel handling process, memory, and device-driver management, plus power management tuned for mobile; sitting above it are core libraries and the Dalvik virtual machine, specifically designed for mobile devices with limited memory and CPU speed.

Android, phần lớn do Google phát triển dưới Open Handset Alliance, là 1 nền tảng di động mã nguồn mở, miễn phí, dựa trên Linux. Kernel của nó là 1 nhân Linux đã chỉnh sửa, lo quản lý tiến trình, bộ nhớ, device driver, cộng thêm quản lý điện năng riêng cho di động; nằm trên đó là các thư viện lõi và máy ảo Dalvik, được thiết kế riêng cho thiết bị di động có bộ nhớ và tốc độ CPU hạn chế.

Applications are written in Java using the Android API, compiled into bytecode, and turned into an executable that runs inside the Dalvik VM — never running as native machine code the way a compiled C program does. Android also bundles its own libraries: a version of webkit for browsers, SQLite for structured data, and libraries for multimedia playback, running on top of a smaller libc than a typical Linux distribution uses.

Ứng dụng được viết bằng Java dùng Android API, biên dịch thành bytecode, rồi biến thành 1 file thực thi chạy bên trong Dalvik VM — không bao giờ chạy dưới dạng mã máy gốc như 1 chương trình C đã biên dịch. 09 · Practice

From source code to a tunable, running kernel

Từ mã nguồn tới 1 kernel chạy được và tinh chỉnh được

Everything so far has been about structure on paper. This last stretch is what actually happens on a real machine — building the kernel, booting it, and then watching it work (or misbehave) once it's alive.

Mọi thứ từ đầu tới giờ mới chỉ là cấu trúc trên giấy. Chặng cuối này là những gì thực sự xảy ra trên 1 máy thật — build kernel, boot nó lên, rồi quan sát nó chạy (hoặc chạy sai) khi đã "sống".

Building a brand-new operating system generally follows the same handful of steps regardless of target: write the OS source code, configure it for the specific target system, compile that source, install the resulting OS, and boot the computer with the freshly built system.

Xây 1 hệ điều hành hoàn toàn mới nhìn chung theo cùng vài bước, bất kể hệ đích là gì: viết mã nguồn OS, cấu hình nó cho đúng hệ đích, biên dịch mã nguồn đó, cài đặt OS vừa build ra, rồi boot máy tính với hệ thống mới build.
Write the operating-system source code
Configure it for the specific target system
Compile the OS
Install the operating system
Boot the computer with the new OS

Building and booting Linux specifically makes those steps concrete: download the Linux source code from kernel.org, configure it with make menuconfig, then compile with make — which produces vmlinuz, the actual kernel image. Kernel modules are compiled separately via make modules, installed into that image with make modules_install, and the whole new kernel is finally installed onto the system with make install.

Build và boot Linux cụ thể sẽ làm rõ các bước đó: tải mã nguồn Linux từ kernel.org, cấu hình bằng make menuconfig, rồi biên dịch bằng make — cho ra vmlinuz, chính là ảnh kernel thật sự. Module kernel được biên dịch riêng qua make modules, cài vào ảnh đó bằng make modules_install, và cuối cùng cả kernel mới được cài vào hệ thống bằng make install.
$ make menuconfig
$ make
→ builds vmlinuz
$ make modules && make modules_install
$ make install

Once you reboot, the machine has to actually find and start that new kernel — the system boot sequence. It begins with a small piece of code called the bootstrap loader, stored in firmware such as the BIOS or, on newer machines, UEFI; its whole job is to locate the kernel, load it into memory, and start it running. Multiboot systems often use a boot manager like GRUB, which asks which kernel and options to load from possibly several disks and partitions.

Sau khi khởi động lại, máy phải thực sự tìm và chạy kernel mới đó — chuỗi boot hệ thống. Nó bắt đầu bằng 1 đoạn mã nhỏ gọi là bootstrap loader, nằm trong firmware như BIOS, hay trên máy đời mới hơn là UEFI; việc của nó chỉ là tìm kernel, nạp vào bộ nhớ, rồi khởi chạy. Hệ đa boot thường dùng 1 trình quản lý boot như GRUB, hỏi cần nạp kernel nào và tùy chọn gì, từ khả năng nhiều ổ đĩa và phân vùng khác nhau.
Power on — CPU begins execution at a fixed hardware address
Bootstrap loader (in BIOS/UEFI firmware) locates the kernel image
Boot manager (e.g. GRUB) may ask which kernel/options to load
Kernel is loaded into memory and begins running

Once an OS is actually running, two related jobs never really stop: debugging (finding and fixing bugs) and performance tuning (removing bottlenecks so the system runs faster). Debugging leans on log files recording significant system events, and on trace listings of the most recent system calls a process made — both invaluable evidence when something goes wrong.

Một khi OS thực sự chạy, 2 việc liên quan không bao giờ thật sự dừng lại: debug (tìm và sửa lỗi) và tinh chỉnh hiệu năng (loại bỏ nút thắt cổ chai để hệ thống chạy nhanh hơn). Debug dựa vào file log ghi lại các sự kiện quan trọng của hệ thống, và các bản ghi trace liệt kê các system call gần nhất mà 1 tiến trình đã gọi — cả 2 đều là bằng chứng vô giá khi có sự cố xảy ra.
[12:03:11] process 4021 opened /etc/config
[12:03:12] syscall write() returned 0

To improve performance, the OS itself must provide the means to compute and display measures of overall system behavior — familiar tools like the Linux top program or the Windows Task Manager give exactly that: a live view of CPU, memory, and process activity, so bottlenecks become visible instead of invisible.

Để cải thiện hiệu năng, chính OS phải cung cấp cách tính toán và hiển thị các số đo hành vi tổng thể của hệ thống — công cụ quen thuộc như chương trình top trên Linux hay Task Manager trên Windows cho đúng thứ đó: 1 góc nhìn trực tiếp về CPU, bộ nhớ, hoạt động tiến trình, để nút thắt cổ chai trở nên hiện hình thay vì vô hình.
📊
top / Task Managergóc nhìn sống về CPU, bộ nhớ, tiến trình — để thấy nút thắt cổ chai đang nằm ở đâu.

Beyond simple monitoring, more advanced profiling tools sample a running program's instruction pointer at regular time intervals, building up a statistical picture of where the program actually spends its time. Several specific tools have become standard in the field: strace traces system calls a process makes, gdb is a source-level interactive debugger, perf collects a whole suite of Linux performance-counter statistics, and tcpdump captures network packets for inspection.

Xa hơn việc theo dõi đơn giản, công cụ profiling nâng cao hơn lấy mẫu con trỏ lệnh (instruction pointer) của chương trình đang chạy theo chu kỳ đều đặn, dựng nên 1 bức tranh thống kê cho biết chương trình thực sự tốn thời gian ở đâu. Vài công cụ cụ thể đã trở thành chuẩn trong ngành: strace ghi lại các system call mà 1 tiến trình gọi, gdb là trình debug tương tác ở mức mã nguồn, perf thu thập cả bộ số liệu performance-counter của Linux, và tcpdump bắt các gói tin mạng để soi xét.
strace

Traces every system call a process makes — great for "what is this program actually asking the kernel for?"

gdb

Interactive, source-level debugger — step through code line by line, inspect variables.

perf

A whole collection of Linux performance-counter tools bundled together.

tcpdump

Captures raw network packets so you can inspect exactly what's being sent and received.

The most powerful modern option is BCC (BPF Compiler Collection): a rich toolkit for creating efficient tracing tools that span both user-level and kernel code in one session, built on the Linux kernel's BPF facility. A classic example script, disksnoop.py, traces every disk I/O request as it happens, in real time — a spiritual descendant of Solaris's earlier DTrace tracing framework.

Lựa chọn mạnh nhất hiện đại là BCC (BPF Compiler Collection): 1 bộ công cụ phong phú để tạo ra công cụ trace hiệu quả, bao trùm cả code ở mức người dùng lẫn kernel trong cùng 1 phiên, xây trên cơ chế BPF của nhân Linux. 1 script ví dụ kinh điển, disksnoop.py, trace từng yêu cầu I/O đĩa ngay khi nó xảy ra, theo thời gian thực — có thể coi là hậu duệ tinh thần của framework trace DTrace trước đây trên Solaris.
