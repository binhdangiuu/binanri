01 · Concept

What exactly is a process?

Tiến trình thực sự là cái gì?

An operating system runs a variety of programs, and every one of them runs as a process — but "process" means something much more specific than "program."

Hệ điều hành chạy đủ loại chương trình, và mỗi chương trình chạy dưới dạng 1 tiến trình — nhưng "tiến trình" (process) mang nghĩa cụ thể hơn nhiều so với "chương trình" (program).
Before the list — take a guess: if two students double-click the exact same game.exe at the same time, is that one process or two? Trước khi đọc tiếp — thử đoán: nếu 2 sinh viên cùng nhấp đúp vào đúng file game.exe cùng lúc, đó là 1 tiến trình hay 2?

A process is a program in execution, and its execution must progress in strictly sequential fashion. A process is more than just the code: it has multiple parts — the text section (the program code itself), the current activity (program counter and processor registers), a stack section holding temporary data such as function parameters, return addresses and local variables, a data section holding global variables, and a heap section holding memory allocated dynamically at run time.

Một tiến trình là 1 chương trình đang chạy, và việc thực thi của nó phải tiến triển theo trình tự tuần tự. Tiến trình không chỉ là đoạn mã: nó có nhiều phần — vùng text (chính mã chương trình), hoạt động hiện tại (program counter và thanh ghi CPU), vùng stack chứa dữ liệu tạm như tham số hàm, địa chỉ trả về, biến cục bộ, vùng data chứa biến toàn cục, và vùng heap chứa bộ nhớ cấp phát động lúc chạy.

A program is a passive entity, just an executable file sitting on disk; a process is an active entity — a program becomes a process the moment its executable file is loaded into memory. Execution can start via a GUI mouse-click, typing its name at a command line (CLI), and so on. Crucially, one program can be several processes at once — think of many users running the same text editor simultaneously; each gets its own process, its own stack, heap and data, even though the text section (the code) may be shared.

Một chương trình là thực thể thụ động, chỉ là 1 file thực thi nằm trên đĩa; 1 tiến trình là thực thể chủ động — chương trình trở thành tiến trình ngay khi file thực thi được nạp vào bộ nhớ. Có thể khởi chạy qua nhấp chuột GUI, gõ tên ở dòng lệnh (CLI), v.v. Quan trọng: 1 chương trình có thể là nhiều tiến trình cùng lúc — hình dung nhiều người dùng cùng chạy 1 trình soạn thảo văn bản; mỗi người có tiến trình riêng, stack/heap/data riêng, dù vùng text (mã) có thể dùng chung.

As a process executes, it changes state: New — the process is being created; Running — instructions are actually being executed; Waiting — the process is waiting for some event to occur (like I/O completion); Ready — the process is waiting to be assigned to a processor; and Terminated — the process has finished execution.

Khi 1 tiến trình chạy, nó đổi trạng thái: New — đang được tạo; Running — lệnh đang thực thi; Waiting — đang chờ 1 sự kiện xảy ra (như hoàn tất I/O); Ready — đang chờ được cấp CPU; và Terminated — đã chạy xong.
⏳

Every process the OS tracks is represented by a Process Control Block (PCB), also called a Task Control Block (TCB). It bundles together: process state, process number (its identity), program counter, CPU registers, CPU-scheduling info (priorities, queue pointers), memory-management information, accounting information (CPU used, elapsed clock time, time limits), and I/O status information (devices allocated, list of open files).

Mọi tiến trình mà OS theo dõi được biểu diễn bằng Process Control Block (PCB), còn gọi Task Control Block (TCB). Nó gom lại: trạng thái tiến trình, số hiệu tiến trình (định danh), program counter, thanh ghi CPU, thông tin lập lịch CPU (độ ưu tiên, con trỏ hàng đợi), thông tin quản lý bộ nhớ, thông tin kế toán (CPU đã dùng, thời gian trôi qua, giới hạn thời gian), và thông tin trạng thái I/O (thiết bị được cấp, danh sách file đang mở).

So far a process has had a single thread of execution — one program counter. A thread gives a process multiple program counters, so multiple locations of the same process can execute at once; this just means the PCB now has to store multiple program counters instead of one. In Linux, every process is represented by the C structure task_struct, holding its pid, state, scheduling time_slice, a pointer to its parent, a list of its children, its open files, and its address space.

Từ đầu tới giờ, 1 tiến trình chỉ có 1 luồng (thread) thực thi — 1 program counter. 1 thread cho tiến trình nhiều program counter, để nhiều vị trí của cùng 1 tiến trình chạy song song; chỉ đơn giản là PCB giờ phải lưu nhiều program counter thay vì 1. Trong Linux, mỗi tiến trình được biểu diễn bằng struct C task_struct, chứa pid, trạng thái, time_slice lập lịch, con trỏ tới tiến trình cha, danh sách con, file đang mở, và không gian địa chỉ.

Zooming into one real C program shows exactly where each variable lands. argc/argv and the stack sit at high memory (parameters, local variables like int y = 15; live here); the heap grows upward from the middle (anything returned by malloc() lands here); uninitialized data and initialized data (global variables) sit below that; and the text section — the compiled instructions of main() itself — sits at the very bottom, low memory.

Soi vào 1 chương trình C thật cho thấy chính xác mỗi biến nằm ở đâu. argc/argv và stack nằm ở vùng nhớ cao (tham số, biến cục bộ như int y = 15; nằm ở đây); heap lớn dần lên từ giữa (bất cứ gì malloc() trả về đều nằm ở đây); uninitialized data và initialized data (biến toàn cục) nằm dưới đó; và vùng text — mã lệnh đã biên dịch của chính main() — nằm ở đáy, vùng nhớ thấp nhất.
/* Memory Layout of a C Program */ #include <stdio.h> #include <stdlib.h> int x; // uninitialized data int y = 15; // initialized data int main(int argc, char *argv[]) // high memory: argc, argv { int *values; // stack: local pointer int i; // stack: local variable values = (int *)malloc(sizeof(int)*5); // heap for (i = 0; i < 5; i++) values[i] = i; return 0; // text: instructions live here, low memory }

02 · Scheduling

Who gets the CPU next?

Ai được cấp CPU tiếp theo?

The whole point of scheduling is to maximize CPU use by quickly switching processes onto a CPU core the instant one leaves.

Mục tiêu của lập lịch là tối đa hóa việc dùng CPU bằng cách chuyển tiến trình khác vào ngay khi 1 tiến trình rời CPU.

The process scheduler selects one process among all available (ready) processes for the next execution on a CPU core. To do this it maintains scheduling queues: the ready queue holds every process residing in main memory that is ready and waiting to execute, while separate wait queues hold processes waiting for a specific event, such as I/O. Processes constantly migrate among these queues as their state changes.

Process scheduler chọn 1 tiến trình trong số các tiến trình sẵn sàng (ready) để chạy tiếp trên 1 nhân CPU. Để làm việc này nó duy trì hàng đợi lập lịch: ready queue chứa mọi tiến trình đang ở bộ nhớ chính, sẵn sàng chờ chạy, còn các wait queue riêng chứa tiến trình đang chờ 1 sự kiện cụ thể, như I/O. Tiến trình liên tục di chuyển giữa các hàng đợi này khi trạng thái đổi.
new process → nhập ready queue
ready queue → CPU (được dispatch)
CPU → I/O wait queue (nếu cần I/O) → thiết bị I/O → quay lại ready queue
CPU → time slice expired → quay lại ready queue
CPU → tạo tiến trình con → chờ ở child-termination wait queue → khi con kết thúc, quay lại ready queue
CPU → chờ interrupt → interrupt wait queue → khi interrupt xảy ra, quay lại ready queue

A context switch occurs when the CPU switches from one process to another. When this happens, the system must save the state of the old process and load the saved state for the new process — and that context is exactly what's represented in the PCB. Context-switch time is pure overhead: the system does no useful work while switching, and the more complex the OS and its PCB, the longer a switch takes. Its actual duration is dependent on hardware support — some hardware provides multiple sets of registers per CPU, letting multiple contexts be loaded at once.

1 context switch xảy ra khi CPU chuyển từ tiến trình này sang tiến trình khác. Lúc đó, hệ thống phải lưu trạng thái của tiến trình cũ và nạp trạng thái đã lưu của tiến trình mới — và context đó chính là những gì được biểu diễn trong PCB. Thời gian context-switch hoàn toàn là overhead: hệ thống không làm việc có ích gì trong lúc chuyển, và OS/PCB càng phức tạp thì switch càng lâu. Thời gian thực tế phụ thuộc phần cứng — vài phần cứng có nhiều bộ thanh ghi trên 1 CPU, cho phép nạp nhiều context cùng lúc.

Mobile systems handle multitasking differently because of limited screen space. Early iOS versions allowed only one process — a single foreground process controlled via the UI — to run; everything else became a suspended, limited background process (a single short task, event notifications, or specific long-running tasks like audio playback). Android runs foreground and background processes with far fewer limits: a background process uses a service to keep performing tasks even after being suspended, and that service has no user interface and a small memory footprint.

Hệ điều hành di động xử lý multitasking khác đi vì màn hình có hạn. iOS đời đầu chỉ cho 1 tiến trình chạy — 1 foreground process duy nhất, điều khiển qua UI; mọi cái khác thành background process bị treo, giới hạn (1 tác vụ ngắn, nhận thông báo sự kiện, hoặc vài tác vụ chạy dài đặc biệt như phát nhạc). Android chạy foreground và background với ít giới hạn hơn nhiều: 1 background process dùng 1 service để tiếp tục làm việc kể cả khi bị treo, service đó không có giao diện và tốn ít bộ nhớ.

03 · Lifecycle

Being born, and dying, as a process

Sinh ra, và chết đi, với tư cách 1 tiến trình

Every system needs mechanisms for two operations: process creation and process termination.

Mọi hệ thống cần cơ chế cho 2 thao tác: tạo tiến trình và kết thúc tiến trình.

Parent processes create children processes, which in turn create other processes, forming a whole tree of processes. Each process is identified and managed via a Process Identifier (PID). Parents and children have resource-sharing options: parent and children may share all resources, children may share only a subset of the parent's resources, or parent and child may share no resources at all. There are also execution options — parent and children can execute concurrently, or the parent can wait until its children terminate — and address-space options: the child can be a duplicate of the parent, or have an entirely new program loaded into it.

Tiến trình cha tạo tiến trình con, con lại tạo tiến trình khác, hình thành cây tiến trình (tree of processes). Mỗi tiến trình được định danh và quản lý qua Process Identifier (PID). Cha và con có tùy chọn chia sẻ tài nguyên: chia sẻ tất cả, chỉ chia sẻ 1 phần, hoặc không chia sẻ gì. Cũng có tùy chọn thực thi — cha và con chạy song song, hoặc cha chờ (wait) con kết thúc — và tùy chọn không gian địa chỉ: con có thể là bản sao của cha, hoặc được nạp 1 chương trình hoàn toàn mới.

On UNIX, fork() creates a new process by duplicating the caller: the child gets pid = 0 from the returned value, the parent gets the child's actual pid (> 0), and a negative return means the fork failed. exec() is then used after a fork to replace the process' entire memory space with a new program. The parent process calls wait() to block until the child terminates. The system() call is a shortcut that hands its command argument straight to the shell interpreter (/bin/sh -c <command>) — it returns -1 if the child process couldn't be created.

Trên UNIX, fork() tạo 1 tiến trình mới bằng cách nhân bản tiến trình gọi nó: con nhận về giá trị pid = 0, cha nhận về pid thật của con (> 0), giá trị âm nghĩa là fork thất bại. exec() dùng sau fork để thay toàn bộ vùng nhớ của tiến trình bằng 1 chương trình mới. Tiến trình cha gọi wait() để chờ (block) tới khi con kết thúc. Lời gọi system() là 1 lối tắt, đưa thẳng đối số command cho shell (/bin/sh -c <command>) — trả về -1 nếu không tạo được tiến trình con.
/* fork a separate process */ pid_t pid = fork(); if (pid < 0) { /* error occurred */ fprintf(stderr, "Fork Failed"); } else if (pid == 0) { /* child process */ execlp("/bin/ls","ls",NULL); } else { /* parent process */ wait(NULL); /* wait for child */ printf("Child Complete"); }

Windows has no fork()/exec() pair — instead a single Windows API call, CreateProcess(), does both jobs at once: it directly launches a brand-new process running a specified program, filling in a STARTUPINFO and a PROCESS_INFORMATION structure, and the parent then calls WaitForSingleObject() — the Windows equivalent of wait() — to block until that child finishes.

Windows không có cặp fork()/exec() — thay vào đó, 1 lời gọi Windows API duy nhất, CreateProcess(), làm cả 2 việc cùng lúc: khởi chạy trực tiếp 1 tiến trình hoàn toàn mới chạy 1 chương trình được chỉ định, điền vào cấu trúc STARTUPINFO và PROCESS_INFORMATION, rồi tiến trình cha gọi WaitForSingleObject() — tương đương wait() bên Windows — để chờ tới khi con đó kết thúc.
/* Creating a Separate Process via Windows API */ #include <stdio.h> #include <windows.h> int main(VOID) { STARTUPINFO si; PROCESS_INFORMATION pi; ZeroMemory(&si, sizeof(si)); si.cb = sizeof(si); ZeroMemory(&pi, sizeof(pi)); /* create child process */ if (!CreateProcess(NULL, "C:\\WINDOWS\\system32\\mspaint.exe", NULL, NULL, FALSE, 0, NULL, NULL, &si, &pi)) { fprintf(stderr, "Create Process Failed"); return -1; } /* parent waits for the child to complete */ WaitForSingleObject(pi.hProcess, INFINITE); printf("Child Complete"); CloseHandle(pi.hProcess); CloseHandle(pi.hThread); }

Thử sức: printf("Hello\n"); fork(); fork(); printf("Hello\n"); — có bao nhiêu tiến trình được tạo ra tổng cộng, và "Hello" (dòng 2) in ra bao nhiêu lần? Gợi ý: mỗi lần gọi fork() nhân đôi số tiến trình đang tồn tại tại thời điểm đó. 2 lần fork() liên tiếp → 1 → 2 → 4 tiến trình. Dòng printf thứ 2 chạy trên cả 4 tiến trình → in 4 lần "Hello".
Thử sức #2: for (i = 0; i < n; i++) fork(); — với n = 2, tổng cộng có bao nhiêu tiến trình tồn tại sau vòng lặp? Gợi ý: đây là fork() có điều kiện, chạy trong vòng lặp — mỗi vòng lặp lại nhân đôi số tiến trình đang tồn tại, kể cả những tiến trình vừa được tạo ra ở vòng trước cũng tự chạy tiếp vòng lặp và tự fork(). Với n = 2: 1 → 2 → 4 tiến trình (giống công thức 2ⁿ tính từ 1 tiến trình gốc).

Every new process gets a unique Process ID assigned by the OS, and every process has a parent process — except the very first one, systemd (pid = 1) on Linux. A process can read its own and its parent's identifiers with getpid() and getppid(); tools like htop and pstree let you watch these parent–child relationships live on a running system.

Mỗi tiến trình mới được OS cấp 1 Process ID duy nhất, và mọi tiến trình đều có tiến trình cha — trừ tiến trình đầu tiên, systemd (pid = 1) trên Linux. 1 tiến trình có thể đọc định danh của chính nó và của cha nó bằng getpid() và getppid(); công cụ như htop và pstree cho xem trực tiếp quan hệ cha–con này trên hệ thống đang chạy.
/* Process IDs */ #include <stdio.h> #include <unistd.h> int main() { printf("The process ID is %d\n", (int) getpid()); printf("The parent process ID is %d\n", (int) getppid()); sleep(100); return 0; } $ ./pid The process ID is 6790 The parent process ID is 6579 $ htop # theo dõi tiến trình & tài nguyên trực tiếp 6579 ltvan 32 0 4196M 1240 ? 0.0 0.0 0:00.00 └─ -bash 6714 ltvan 25 0 4168M 696 ? 0.0 0.0 0:00.00 └─ ./pid

A process executes its last statement and then asks the OS to delete it via the exit() system call, which returns status data to the parent (through wait()) and lets the OS deallocate the process' resources. A parent may instead forcibly terminate a child via abort() — say, because the child exceeded its allocated resources, its task is no longer needed, or the parent itself is exiting and the OS does not allow a child to outlive its parent. When a process terminates, all its children must also be terminated in what's called cascading termination — initiated by the OS itself, killing children, grandchildren, and so on.

1 tiến trình chạy lệnh cuối cùng rồi xin OS xóa nó qua exit(), trả dữ liệu trạng thái về cho cha (qua wait()) và cho OS giải phóng tài nguyên của tiến trình. Cha cũng có thể ép buộc kết thúc con qua abort() — vì con vượt tài nguyên được cấp, tác vụ của con không cần nữa, hoặc chính cha đang thoát và OS không cho con sống lâu hơn cha. Khi 1 tiến trình kết thúc, mọi con của nó cũng phải kết thúc theo, gọi là cascading termination — do chính OS khởi xướng, giết con, cháu, v.v.

The parent process may wait for a child's termination via wait(&status), which returns status information plus the pid of the terminated child — equivalent to waitpid(-1, &status, 0). If no parent is waiting, the terminated process becomes a zombie; if the parent terminates without ever calling wait(), the leftover child becomes an orphan.

Tiến trình cha có thể chờ con kết thúc qua wait(&status), trả về thông tin trạng thái cùng pid của con vừa kết thúc — tương đương waitpid(-1, &status, 0). Nếu không có cha nào đang chờ, tiến trình kết thúc trở thành zombie; nếu cha kết thúc mà chưa từng gọi wait(), tiến trình con còn sót lại trở thành orphan.

04 · IPC

Why (and how) do processes talk?

Vì sao (và bằng cách nào) các tiến trình nói chuyện được với nhau?

Processes within a system may be independent or cooperating — and cooperating processes are what create the need for Inter-Process Communication (IPC).

Tiến trình trong 1 hệ thống có thể độc lập (independent) hoặc hợp tác (cooperating) — và chính tiến trình hợp tác tạo ra nhu cầu Giao tiếp Liên tiến trình (IPC).

An independent process does not share data with any other process executing in the system, while a cooperating process can affect, or be affected by, other processes — including sharing data with them. Reasons for cooperating include: information sharing, computation speed-up (splitting a task across processes), modularity (dividing system functions into separate processes), and plain convenience. All of this requires Inter-Process Communication (IPC).

1 tiến trình độc lập không chia sẻ dữ liệu với bất kỳ tiến trình nào khác đang chạy trong hệ thống, còn 1 tiến trình hợp tác có thể tác động, hoặc bị tác động, bởi tiến trình khác — kể cả chia sẻ dữ liệu với nhau. Lý do để hợp tác gồm: chia sẻ thông tin, tăng tốc tính toán (chia nhỏ 1 việc cho nhiều tiến trình), module hóa (chia chức năng hệ thống thành các tiến trình riêng), và đơn giản là tiện lợi. Tất cả những điều này cần IPC.

There are exactly two models of IPC: shared memory and message passing. In shared memory, an area of memory is set up so both process A and process B can read/write it directly, with the communication under the control of the user processes, not the OS — the major issue then is providing a mechanism to let those processes synchronize their actions when accessing the shared region. In message passing, processes exchange messages that are placed in a queue managed by the kernel, without ever resorting to shared variables.

Có đúng 2 mô hình IPC: shared memory (bộ nhớ dùng chung) và message passing (truyền thông điệp). Với shared memory, 1 vùng bộ nhớ được thiết lập để cả tiến trình A và B đọc/ghi trực tiếp, việc giao tiếp nằm dưới sự kiểm soát của tiến trình người dùng, không phải OS — vấn đề chính lúc này là cung cấp cơ chế để các tiến trình đồng bộ hành động khi truy cập vùng dùng chung đó. Với message passing, tiến trình trao đổi thông điệp được đặt vào 1 hàng đợi do kernel quản lý, không bao giờ cần đến biến dùng chung.

  • Nhanh hơn (sau khi thiết lập)
  • OS chỉ set up vùng nhớ, không can thiệp nữa
  • Cần tự đồng bộ (dễ race condition)
Message passing

Gửi/nhận message qua kernel, không dùng chung biến.

  • Dễ hiện thực đúng hơn (kernel lo đồng bộ)
  • Chậm hơn vì luôn qua kernel
  • Hữu ích khi liên lạc qua mạng

The classic paradigm for cooperating processes is the producer–consumer problem: a producer process produces information that is consumed by a consumer process. An unbounded buffer places no practical limit on buffer size; a bounded buffer assumes a fixed buffer size, using an in pointer to the next free slot and an out pointer to the first full slot — this shared-memory solution is correct, but can only ever use BUFFER_SIZE - 1 elements (to distinguish "full" from "empty," since both would otherwise look like in == out).

Mô hình kinh điển cho tiến trình hợp tác là bài toán producer–consumer: 1 tiến trình sản xuất tạo ra thông tin để 1 tiến trình tiêu thụ dùng. unbounded buffer không giới hạn thực tế kích thước buffer; bounded buffer giả sử buffer có kích thước cố định, dùng con trỏ in trỏ tới ô trống kế tiếp và out trỏ tới ô đầy đầu tiên — giải pháp shared-memory này đúng, nhưng chỉ dùng được tối đa BUFFER_SIZE - 1 phần tử (để phân biệt "đầy" với "rỗng", nếu không cả 2 đều trông giống in == out).
/* producer */ while (true) { while (((in + 1) % BUFFER_SIZE) == out) ; /* buffer full — do nothing */ buffer[in] = next_produced; in = (in + 1) % BUFFER_SIZE; } /* consumer */ while (true) { while (in == out) ; /* buffer empty — do nothing */ next_consumed = buffer[out]; out = (out + 1) % BUFFER_SIZE; }
Mẹo thi "Bounded buffer chỉ dùng được BUFFER_SIZE − 1 phần tử" — nhớ chính xác con số này, đề rất hay hỏi trực tiếp lý do tại sao (để phân biệt full vs empty bằng con trỏ in/out).

05 · IPC

Send, receive, and everything in between

Gửi, nhận, và mọi thứ ở giữa

Message passing is a mechanism for processes to communicate AND to synchronize their actions, all through two primitive operations.

Message passing là cơ chế để tiến trình giao tiếp VÀ đồng bộ hành động, tất cả qua 2 thao tác nguyên thủy.

The IPC facility provides exactly two operations: send(message) and receive(message), with message size either fixed or variable. If processes P and Q wish to communicate, they must first establish a communication link between them, then exchange messages via send/receive. This raises real implementation questions: how are links established? Can a link be shared by more than two processes? How many links can exist between one pair of processes? What's a link's capacity, message-size limit, and is it unidirectional or bi-directional?

Dịch vụ IPC cung cấp đúng 2 thao tác: send(message) và receive(message), kích thước message có thể cố định hoặc thay đổi. Nếu 2 tiến trình P và Q muốn giao tiếp, trước hết chúng phải thiết lập 1 đường liên kết (communication link), rồi trao đổi message qua send/receive. Điều này đặt ra câu hỏi hiện thực thật sự: link được thiết lập ra sao? 1 link có thể dùng chung cho hơn 2 tiến trình không? Có bao nhiêu link giữa 1 cặp tiến trình? Dung lượng link, giới hạn kích thước message, và link 1 chiều hay 2 chiều?

In direct communication, processes must name each other explicitly: send(P, message) sends to process P, receive(Q, message) receives from process Q. Links here are established automatically, exactly one link exists per pair, and each link is usually bi-directional (though it may be unidirectional). In indirect communication, messages are instead directed to and received from mailboxes (also called ports): each mailbox has a unique ID, and processes can communicate only if they share one. A link is established only when processes share a common mailbox, one link may serve many processes, and a pair of processes may even share several links.

Trong giao tiếp trực tiếp (direct communication), tiến trình phải gọi tên nhau tường minh: send(P, message) gửi tới tiến trình P, receive(Q, message) nhận từ tiến trình Q. Link ở đây tự động thiết lập, đúng 1 link cho mỗi cặp, và thường 2 chiều (dù có thể 1 chiều). Trong giao tiếp gián tiếp (indirect communication), message thay vào đó gửi tới/nhận từ hộp thư (mailbox) (còn gọi port): mỗi mailbox có 1 ID duy nhất, tiến trình chỉ giao tiếp được nếu dùng chung mailbox. Link chỉ thiết lập khi các tiến trình dùng chung 1 mailbox, 1 link có thể phục vụ nhiều tiến trình, và 1 cặp tiến trình còn có thể dùng chung nhiều link.

Mailbox sharing raises a puzzle: if P1, P2, and P3 all share mailbox A, and P1 sends while P2 and P3 both receive — who actually gets the message? Three solutions exist: allow a link to be associated with at most two processes, allow only one process at a time to execute a receive, or let the system pick the receiver arbitrarily and notify the sender who got it.

Việc chia sẻ mailbox đặt ra 1 câu hỏi: nếu P1, P2, P3 cùng dùng mailbox A, P1 gửi còn P2 và P3 đều nhận — ai thực sự nhận được message? Có 3 giải pháp: giới hạn 1 link chỉ cho tối đa 2 tiến trình, chỉ cho 1 tiến trình tại 1 thời điểm được thực hiện receive, hoặc để hệ thống tự chọn người nhận và báo cho người gửi biết ai đã nhận.

Message passing may be blocking (considered synchronous) or non-blocking (considered asynchronous). A blocking send keeps the sender blocked until the message is received; a blocking receive keeps the receiver blocked until a message becomes available. A non-blocking send lets the sender fire the message and continue immediately; a non-blocking receive either gets a valid message, or a null message right away. If both send and receive block, the result is called a rendezvous.

Message passing có thể là blocking (coi là đồng bộ) hoặc non-blocking (coi là bất đồng bộ). Blocking send giữ người gửi bị chặn tới khi message được nhận; blocking receive giữ người nhận bị chặn tới khi có message. Non-blocking send cho người gửi bắn message rồi chạy tiếp ngay; non-blocking receive hoặc nhận được message hợp lệ, hoặc nhận null ngay lập tức. Nếu cả send và receive đều blocking, kết quả gọi là rendezvous.

Finally, every link has a message queue attached, implemented one of three ways. Zero capacity means no messages are ever queued on the link — the sender must wait for the receiver, i.e. a rendezvous. Bounded capacity means a finite queue of n messages, forcing the sender to wait once the link is full. Unbounded capacity means an infinite-length queue, so the sender never waits.

Cuối cùng, mỗi link có 1 hàng đợi message đính kèm, cài đặt theo 1 trong 3 cách. Zero capacity nghĩa là không message nào được xếp hàng trên link — người gửi phải chờ người nhận, tức rendezvous. Bounded capacity nghĩa là hàng đợi hữu hạn n message, buộc người gửi phải chờ khi link đầy. Unbounded capacity nghĩa là hàng đợi vô hạn, người gửi không bao giờ phải chờ.

06 · Case studies

How real operating systems do IPC

Hệ điều hành thật cài đặt IPC ra sao

POSIX, Mach, and Windows each take a slightly different approach — one shared-memory-centric, the others message-based.

POSIX, Mach, và Windows mỗi cái đi 1 hướng hơi khác nhau — 1 bên thiên về shared memory, 2 bên còn lại thiên về message.

POSIX shared memory works like this: a process first creates a shared memory segment with shm_open(name, O_CREAT | O_RDWR, 0666) (the same call also opens an existing segment), sets the object's size with ftruncate(shm_fd, size), then uses mmap() to memory-map a file pointer to that shared object. From then on, reading and writing to shared memory is done simply through the pointer mmap() returned.

POSIX shared memory hoạt động như sau: 1 tiến trình trước hết tạo 1 đoạn shared memory bằng shm_open(name, O_CREAT | O_RDWR, 0666) (cùng lời gọi này cũng mở được đoạn đã có), đặt kích thước đối tượng bằng ftruncate(shm_fd, size), rồi dùng mmap() để ánh xạ 1 con trỏ file tới đối tượng dùng chung đó. Từ đó, đọc/ghi shared memory chỉ đơn giản qua con trỏ mà mmap() trả về.
shm_open(name, O_CREAT|O_RDWR, 0666) — tạo/mở segment
ftruncate(shm_fd, SIZE) — đặt kích thước
mmap(0, SIZE, PROT_WRITE, MAP_SHARED, shm_fd, 0) — ánh xạ con trỏ ghi (producer) / PROT_READ (consumer)
sprintf(ptr, ...) để ghi, hoặc printf("%s",ptr) để đọc
shm_unlink(name) — xóa segment (bên consumer)

Mach communication is entirely message based — even system calls are messages. Every task gets two ports at creation, a Task Self port and a Notify port; messages are sent and received using the mach_msg() function, and ports needed for communication are created via mach_port_allocate(). Send and receive are very flexible: if the mailbox is full, four options exist — wait indefinitely, wait at most n milliseconds, return immediately, or temporarily cache a message.

Giao tiếp trong Mach hoàn toàn dựa trên message — kể cả system call cũng là message. Mỗi task được cấp 2 port khi tạo, port Task Self và port Notify; message gửi/nhận qua hàm mach_msg(), port cần cho giao tiếp được tạo qua mach_port_allocate(). Gửi và nhận rất linh hoạt: nếu mailbox đầy, có 4 lựa chọn — chờ vô hạn, chờ tối đa n mili-giây, trả về ngay lập tức, hoặc tạm cache message lại.

Windows is message-passing centric via its advanced Local Procedure Call (LPC) facility, which only works between processes on the same system, using ports (like mailboxes) to establish and maintain channels. Communication works as a sequence: the client opens a handle to the subsystem's connection port object and sends a connection request; the server creates two private communication ports and returns a handle to one of them; from then on, client and server each use their own port handle to send messages/callbacks and listen for replies.

Windows thiên về message-passing qua cơ chế Local Procedure Call (LPC) nâng cao, chỉ hoạt động giữa các tiến trình trên cùng 1 hệ thống, dùng port (giống mailbox) để thiết lập và duy trì kênh giao tiếp. Giao tiếp diễn ra theo trình tự: client mở 1 handle tới đối tượng connection port của subsystem và gửi yêu cầu kết nối; server tạo 2 communication port riêng và trả về 1 handle cho client; từ đó, client và server mỗi bên dùng port handle riêng để gửi message/callback và lắng nghe phản hồi.

07 · Networked IPC

From one pipe to a whole network

Từ 1 cái ống tới cả mạng lưới

Pipes let two local processes talk down a single conduit; sockets and RPC extend the same idea across an entire network.

Pipe cho 2 tiến trình cục bộ nói chuyện qua 1 đường ống; socket và RPC mở rộng ý tưởng đó ra khắp mạng.

A pipe acts as a conduit allowing two processes to communicate, but several design questions must be answered: is communication unidirectional or bidirectional? If two-way, is it half or full-duplex? Must the communicating processes have a relationship (e.g. parent–child)? Can the pipe be used over a network? Ordinary pipes cannot be accessed from outside the process that created them — typically a parent creates the pipe and uses it with a child it spawned, writing to the pipe's write-end and reading from its read-end, making them inherently unidirectional and requiring a parent–child relationship. Named pipes are more powerful: communication is bidirectional, no parent–child relationship is required, and several unrelated processes can use the same named pipe — provided on both UNIX and Windows.

1 pipe (ống dẫn) đóng vai trò đường dẫn cho 2 tiến trình giao tiếp, nhưng có vài câu hỏi thiết kế cần trả lời: giao tiếp 1 chiều hay 2 chiều? Nếu 2 chiều, là half hay full-duplex? Các tiến trình giao tiếp có bắt buộc quan hệ (ví dụ cha–con) không? Pipe có dùng qua mạng được không? Ordinary pipe (pipe thường) không truy cập được từ ngoài tiến trình đã tạo nó — thường cha tạo pipe rồi dùng chung với con nó sinh ra, ghi vào đầu ghi (write-end) và đọc từ đầu đọc (read-end), nên bản chất 1 chiều và cần quan hệ cha–con. Named pipe mạnh hơn: giao tiếp 2 chiều, không cần quan hệ cha–con, nhiều tiến trình không liên quan có thể cùng dùng — hỗ trợ trên cả UNIX và Windows.
Ordinary pipe
  • 1 chiều (write-end → read-end)
  • Bắt buộc quan hệ cha–con
  • Không tồn tại ngoài process đã tạo
Named pipe
  • 2 chiều

For genuinely networked IPC, a socket is defined as an endpoint for communication — a concatenation of an IP address and a port, where the port number differentiates network services running on the same host. For example, the socket 161.25.19.8:1625 refers to port 1625 on host 161.25.19.8. All communication happens between a pair of sockets, all ports below 1024 are well known (reserved for standard services), and the special IP address 127.0.0.1 — the loopback address — refers back to the very system the process is running on.

Với IPC thật sự qua mạng, 1 socket được định nghĩa là 1 điểm cuối cho giao tiếp — là chuỗi ghép giữa 1 địa chỉ IP và 1 port, số port dùng để phân biệt các dịch vụ mạng chạy trên cùng 1 host. Ví dụ, socket 161.25.19.8:1625 chỉ port 1625 trên host 161.25.19.8. Mọi giao tiếp diễn ra giữa 1 cặp socket, mọi port dưới 1024 là well known (dành riêng cho dịch vụ chuẩn), và địa chỉ IP đặc biệt 127.0.0.1 — địa chỉ loopback — trỏ ngược lại chính hệ thống đang chạy tiến trình đó.

Java makes sockets concrete in just a few lines. A DateServer opens a ServerSocket on a chosen port and blocks on accept() until a client connects, then writes the current date back down that client's socket. Java also offers three flavors of socket: connection-oriented (TCP) via Socket/ServerSocket, connectionless (UDP), and MulticastSocket, which can send the same data to multiple recipients at once.

Java biến socket thành thứ cụ thể chỉ trong vài dòng. 1 DateServer mở 1 ServerSocket ở port đã chọn và chặn (block) tại accept() tới khi có client kết nối, rồi ghi ngày giờ hiện tại ngược lại qua socket của client đó. Java còn có 3 loại socket: connection-oriented (TCP) qua Socket/ServerSocket, connectionless (UDP), và MulticastSocket, có thể gửi cùng 1 dữ liệu tới nhiều người nhận cùng lúc.
// DateServer.java ServerSocket sock = new ServerSocket(6013); while (true) { Socket client = sock.accept(); PrintWriter pout = new PrintWriter( client.getOutputStream(), true); pout.println(new java.util.Date().toString()); client.close(); // resume listening } // DateClient.java Socket sock = new Socket("127.0.0.1", 6013); BufferedReader bin = new BufferedReader( new InputStreamReader(sock.getInputStream())); String line; while ((line = bin.readLine()) != null) System.out.println(line); sock.close();

Remote Procedure Call (RPC) abstracts procedure calls between processes on networked systems, again differentiated by ports. Stubs act as proxies for the real procedure on both the client and server sides: the client-side stub locates the server and marshals the parameters, and the server-side stub receives that message, unpacks the marshalled parameters, and actually runs the procedure on the server. Different machine architectures — big-endian (e.g. Motorola) vs little-endian (e.g. Intel x86) — are reconciled via a common External Data Representation (XDR) format.

Remote Procedure Call (RPC) trừu tượng hóa lời gọi hàm giữa các tiến trình trên hệ thống nối mạng, cũng phân biệt qua port. Stub đóng vai trò proxy cho hàm thật ở cả 2 phía client và server: client-side stub tìm server và marshal (đóng gói) tham số, server-side stub nhận message đó, giải đóng gói tham số, rồi thực sự chạy hàm trên server. Các kiến trúc máy khác nhau — big-endian (vd Motorola) so với little-endian (vd Intel x86) — được dung hòa qua 1 định dạng chung là External Data Representation (XDR).

Remote communication carries more failure scenarios than local communication (a message can be delivered exactly once rather than merely at most once), so the OS typically provides a rendezvous (or matchmaker) service to actually connect client and server: the client asks the matchmaker daemon which port serves procedure X, gets a port number P back, and only then sends its real RPC directly to a daemon listening on port P.

Giao tiếp từ xa gặp nhiều kịch bản lỗi hơn giao tiếp cục bộ (1 message có thể được gửi đúng 1 lần thay vì chỉ tối đa 1 lần), nên OS thường cung cấp dịch vụ rendezvous (hay matchmaker) để thực sự kết nối client và server: client hỏi daemon matchmaker port nào phục vụ hàm X, nhận về số port P, rồi mới gửi RPC thật trực tiếp tới daemon đang lắng nghe ở port P.
Client → kernel: gửi message tới matchmaker, hỏi port của thủ tục X
Matchmaker tra bảng, trả lời client kèm port P
Kernel đặt port P vào message RPC của user
Kernel gửi RPC thật tới port P trên server
Daemon đang lắng nghe port P xử lý request, gửi output ngược lại client
